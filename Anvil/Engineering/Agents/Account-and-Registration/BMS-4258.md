## Scope report

_Scoped 2026-06-11 by the scope fleet against the develop-only tree; the main merge (a395fe49) landed afterward — footprint may be stale, re-verify paths._

- **AC grade**: D · **Risk**: high
- **Packages**: OHFY-eCommerce, OHFY-eCommerce-UI
- **Depends on**: BMS-3926, BMS-4493

**Approach**: Extend the existing guest registration flow (ecomRegister LWC -> Ecom_UI_Wrappers -> RegisterController.registerUser) so a contact can attach multiple Accounts during one signup: add a repeatable business search/select step in the LWC, change registerUser to accept a list of accountIds, create the Contact under a primary Account, and relate the remaining Accounts (per team direction: one Contact/portal user -> many Account records, presumably via AccountContactRelation). Highest risks are that the ticket has zero acceptance criteria (mechanism, primary-account rule, and UX all unspecified) and that every file involved lives only on the main branch — an autonomous agent working from develop/this worktree would find no ecom code at all and the ecom-setup org recipe is still marked DRAFT with TBD steps.

**AC gaps:**
- Ticket has NO acceptance criteria section at all — only a user-story statement and a scope note deferring the post-login account switcher to a follow-up ticket
- Data-model decision is unstated in the ticket: one Contact related to N Accounts via standard AccountContactRelation (Contacts-to-Multiple-Accounts) vs N Contact records per Account. Memory note project_ecom_multi_account_per_retailer confirms the team direction is one Contact/portal user -> many Account records, but the ticket itself does not say which mechanism, which account is 'primary' (Contact.AccountId), or how the portal user's Account context is set at login
- Registration UX is unspecified: current ecomRegister step 1 selects exactly ONE account from search results — does multi-select happen in one search, or via a repeatable 'add another business' loop (likely needed, since businesses have different names/ZIPs/licenses)?
- Search/eligibility rules per additional account are unspecified: does each added business re-require ZIP + license match? Does the expired-license block apply per account or fail the whole registration?
- Duplicate handling not specified: registerUser currently rejects an existing Contact with same email under the selected account — for multi-account, should an existing contact on Account A absorb new relations to B/C, or hard-fail?
- No verification criteria: no Playwright spec named, no expected post-registration record shape (which Account the User.ContactId account points to, what relation records exist), nothing an agent can assert against
- References the Gulf storefront ('gulf' label) — site name, self-reg page assignment, and which Experience Cloud page hosts ecomRegister are not stated in the ticket
