Putting a dollar sign on "keep extra stock"

A demand planner raises the safety-stock target for a product — "hold 16 days of cover, not the usual 10." That decision costs money: you're now carrying extra cases that tie up cash. BMS-5640 already showed that dollar figure as a preview the moment you type a proposed target. This ticket makes it a standing number — so a manager can pull a report and see, across every override in force right now, how much cash each one is holding above baseline.

Safety stock
Extra buffer inventory kept on purpose so you don't run out when a supplier is late or demand spikes.
DOH
Days on Hand — stock measured in time. "16 DOH" = ~16 days of cover at the current sales pace.
Override
A planner-set, dated record (SKU_Override__c) that raises a product's target DOH above the system default.
Baseline / standard
The target the org would use if the override didn't exist. The extra value is measured against this, not the override's own number.
The output
One dollar figure per override — Estimated Additional Inventory Value — plus the day-delta and a status, all shown as columns on the Safety Stock Overrides report.

Issue · Impact · Solution

GapBMS-5641 AC-2 asked the report to quantify the buffer being held in dollars. The BMS-5640 planning screen only shows that figure per-proposal, at save time — it never became a standing report column. The report exposed raw fields only. (Confirmed unresolved after PR #481, which measures actual-vs-target days, not the $ value.)
ImpactNo way to see, at a glance, the total cash tied up by active overrides — so nobody can review or defend the buffer spend.
SolutionA nightly batch (B_SafetyStockImpact) computes the incremental value each Active override holds above its standard baseline and stamps four fields onto SKU_Override__c. They become standing report columns.
value = ceil( (overrideTarget − standardBaseline) × Average_Daily_Depletion__c ÷ Units_Per_Case__c ) × Average_Case_Cost__c
Go deeper — the formula, with the live worked example

The formula turns a time gap (extra days of cover) into a dollar figure. The key subtlety: the delta is measured against the standard baseline, not the override's own target — because once the override is Active it becomes the effective target, so measuring against "effective" would always yield zero.

Override target16 DOH (the planner's setting) Standard baseline10 DOH (from Inventory_Threshold__c) → delta days16 − 10 = 6 extra days velocity100 units/day (Average_Daily_Depletion__c) units wanted6 × 100 = 600 extra units case size24 units/case (Units_Per_Case__c) → casesceil(600 ÷ 24) = 25 cases case cost$30 (Average_Case_Cost__c) → value25 × $30 = $750

This is the exact scenario stamped live in org bms5754 (see verification below). Rounds cases up (ceiling) — you can't hold a fraction of a case.

✅ Architecturally forced — not a preference

Why a nightly batch-stamp, and not a report formula?

The obvious instinct is a formula field or a trigger. Both are impossible here — the package tier model rules them out.

In plain English: the number needs two ingredients the override record doesn't carry — how fast the product sells (velocity, which lives on the Inventory table) and what the standard target would be (which only a WMS-tier service can work out). A report formula can't reach the first; the code that owns the override can't reach the second. So the value is pre-computed by a background job and written onto the record, exactly like the existing DOI report (BMS-3779) does.

  • No relationship to velocity. There is no path from SKU_Override__c to Inventory__c, and velocity (Average_Daily_Depletion__c) lives on Inventory. A cross-object report formula can't hop a relationship that doesn't exist.
  • Tier wall on the baseline. The standard baseline is resolved by S_InventoryThresholds, which is WMS-tier (3). The SKU_Override__c trigger is PLTFM-tier (2). WMS depends on PLTFM, never the reverse — so the trigger physically cannot call the resolver. The compute must live in WMS.
  • Precedent. This mirrors B_InventoryDOI (BMS-3779): a WMS batch that stamps a computed figure onto a record so a report can display it. Same shape, same reasons.

Consequence for admins: the batch must be registered once per environment (System.schedule('WMS Safety Stock Impact Value', '0 0 2 * * ?', new B_SafetyStockImpact())). Documented in setup.md.

The four estimate statuses — an honest number or an honest "can't"

A missing figure must never read as "$0 impact." Every row gets a status that says why it is or isn't valued.

Delta column is blank only when the standard is unknown (supplier scope) — a dry-run fix: the formula's BlankAsBlank setting keeps a missing standard from silently reading as 0.

Decisions logged for refinement

  • 🧠 Delta is measured vs the STANDARD baseline, not the override's effective target (which would always net to 0). New S_InventoryThresholds.resolveStandardTarget() returns the baseline-only target.
  • 🧠 Can't-estimate shows blank + a status, never $0 — distinct from a genuine at-or-below zero. Four status labels up for ratification.
  • 🧠 No baseline ⇒ standard treated as 0 (whole target counts as additional). Open: should a missing baseline instead be "No Data"?
  • 🟡 Supplier-scope overrides are flagged, not valued — cross-SKU aggregation deferred. Open: do we want supplier-level roll-up as a follow-up?

All four posted to BMS-5754 for the team to ratify.

Want to run it by hand? (org bms5754)

  1. Data is already seeded — four Active overrides, one per status, already stamped by the batch.
  2. To re-run the compute after changing anything: Developer Console → Anonymous Apex → Database.executeBatch(new B_SafetyStockImpact(), 20);
  3. View the values: build a report from the Safety Stock Overrides report type (the four columns are checked-by-default), or open a SKU_Override__c record. The Safety_Stock_Manager_Access permset grants read on the fields.

Jargon legend

monospace = a real field, object, or class in the codebase.

SKU_Override__cA planner-set, dated override raising a product's target DOH. Scope__c is SKU (one item × warehouse) or Supplier (all items of a supplier).
S_SafetyStockImpactThe compute service (WMS). Bulk-queries velocity + packaging once, memoizes baseline resolution, returns the value + status per override.
B_SafetyStockImpactThe Batchable + Schedulable that runs the service across all Active overrides nightly and writes the stamps (SYSTEM_MODE).
S_InventoryThresholdsThe WMS service that resolves target DOH. New method resolveStandardTarget() returns the baseline-only target, ignoring overrides.
Inventory_Threshold__cThe baseline targets, set per warehouse (and optionally per supplier). Source of the "standard" the delta is measured against.
SYSTEM_MODEThe batch runs as a service account and writes regardless of the scheduling user's field security — that's why the value stamps even for users who can't see the field.
StampPre-compute a value and store it on the record (vs. computing it live). Lets a plain report show a figure that would otherwise need cross-object logic.
