BMS-4665 · Product case

The logic works. Now it needs a face.

Minimum Transfer Quantity Thresholds shipped as pure backend enforcement. It correctly blocks bad transfers — but today no one can see what it's doing or manage the rules without editing raw records. This is the case for a front end.

Backend built (PR #355) Front end not started Relates BMS-4666 spike · BMS-4667 reporting
The ask in one line

Fund a small front end with two surfaces — a Threshold Management screen and an enforcement visibility dashboard — so admins can configure rules safely and ops can see blocks, coverage gaps, and compliance. The data and enforcement already exist; only the human layer is missing.

01 Where we are today

The backend is solid and tested. The gap is entirely human-facing: configuration happens in raw record pages, and enforcement is invisible until it slaps someone with an error.

✅ What's built & working

  • Unit-aware enforcement (cases / layers / pallets) at New → In Progress
  • Whole-layer / whole-pallet rounding rules
  • Lane resolution (item + origin/destination), most-specific wins
  • A durable, rollback-proof audit trail (Transfer_Threshold_Event__c)
  • 90% test coverage, no bypass path

❌ What's missing (human layer)

  • No UI to create / manage thresholds — admins edit raw Transfer_Threshold__c records
  • No way to see what's configured vs. what's missing (coverage gaps)
  • Planners only learn a rule exists when the commit fails with a toast
  • The rich audit data has no dashboard — it's collected, not surfaced
  • Easy to misconfigure silently (e.g. Layers unit on an item with no factor → rule skipped)

02 Who feels the gap

Admin / Ops configmaintains the rules
todayOpens a raw record, hand-types a number, guesses whether "1 layer" means the right number of cases, has no validation beyond "> 0", and can't tell which items/lanes already have rules. Misconfigurations are silent.
Warehouse plannermoves the product
todayBuilds a transfer, hits commit, and only then gets a red error toast. No upfront signal that a minimum applies, what it is, or how far short they are until they've already done the work.
Operations managerowns the outcome
todayCan't answer "are these thresholds actually helping?" — no view of how many transfers were blocked, on which lanes, or which items still have no rule. Flying blind on adoption and impact.

03 Surface 1 — Threshold Management

A guided screen to create and maintain rules: lane pickers, a unit selector with a live cases-equivalent preview, real validation, and a coverage view of items/lanes with no rule. Replaces "edit the raw record and hope."

05 Bonus — preventive, not just punitive

A small inline hint on the transfer screen turns a hard stop into guidance — the planner sees the rule before committing, not after.

Update Transfer — Boats Float 1/2 BBL · Milton → Montgomery
💡
Minimum applies on this lane: 1 layer (10 cases), whole layers only. You've staged 3 cases — add 7 to reach 1 layer, or 17 to reach 2. (Commit will be blocked below the minimum.)

06 Why it's worth it

Fewer misconfigurations
Live unit→cases preview + validation + coverage view stop silent mistakes (the wrong number, a Layers rule on an item with no factor, a missing lane).
Adoption you can prove
"142 uneconomical transfers prevented this month" is a number you can take to Gulf. Right now that value is invisible.
Less planner friction
Guidance at staging beats a surprise error at commit — fewer reworked transfers, faster docks.
Self-service config
Admins manage rules without engineering or raw-record spelunking — answers the open "who maintains it" question on BMS-4665.

07 Suggested phasing

DONE
Backend enforcement + audit (BMS-4665, PR #355). The hard part is shipped — config object, rules, rollback-proof audit.
NEXT
Threshold Management LWC — guided create/edit, unit→cases preview, validation, coverage gaps. Directly resolves the open "who maintains it / via what surface" question.
THEN
Visibility dashboard (BMS-4666 spike → BMS-4667 build) over the existing audit object, plus the optional inline planner hint.
Bottom line

We've built an engine with no dashboard and no steering wheel. The enforcement is correct and the audit data is already flowing — a focused front end is what turns invisible, expert-only backend logic into a usable, measurable feature Gulf can actually operate.
