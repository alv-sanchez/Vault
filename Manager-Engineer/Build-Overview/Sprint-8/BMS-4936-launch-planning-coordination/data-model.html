Worked example — how a real record's checklist ties to its lanes

Using the actual demo record PL-00000003. Two separate fields are doing two separate jobs — that's the whole trick.

Product_Launch__c  "PL-00000003"   (Id: a2lEi000001EKW9IAO)
 Launch_Date__c = 07/13/26
 Purchasing_Ready__c        = false  ◄─┐
 Warehouse_Ready__c         = false  ◄─┤
 POS_Ready__c               = false  ◄─┤  4 booleans, ONE per lane —
 Sales_Activation_Ready__c  = false  ◄─┤  computed FROM the children below,
 Readiness_Percent__c       = 13%    ◄─┘  never set directly

        │
        │ S_ProductLaunch.recalculateReadiness (fires on every step insert/update/delete)
        ▼
  1. Pull all 8 rows WHERE Product_Launch__c = a2lEi...EKW9IAO   (the FK — this is the only query filter)
  2. In Apex memory, bucket them by their Lane__c STRING VALUE (plain text match, not a join):
       "Purchasing"           → [Complete, Not Started]        → 1/2 complete → NOT ready
       "Warehouse Readiness"  → [Not Started, Not Started]     → 0/2 complete → NOT ready
       "POS Material"         → [Not Started, Not Started]     → 0/2 complete → NOT ready
       "Sales Activation"     → [Not Started, Not Started]     → 0/2 complete → NOT ready
  3. Write ONE UPDATE back to the parent, one boolean per bucket + overall %:
       Purchasing_Ready__c = false, Warehouse_Ready__c = false,
       POS_Ready__c = false, Sales_Activation_Ready__c = false,
       Readiness_Percent__c = 1/8 = 13%
The one-sentence version: the master-detail field (also confusingly named Product_Launch__c) is the only actual database relationship — it says "this step belongs to that launch." Lane__c is just a text value living on that same row; nothing in the schema forces it to be one of the four canonical strings except application code. The "linkage" you're looking for isn't a foreign key at all — it's a grouping key that Apex uses in memory, every time a step changes, to decide which of the 4 rollup booleans on the parent to rewrite.

Trigger pointClass / methodActionObject touchedWhat happens
Product_Launch__c
after insert		 ProductLaunchTriggerService.afterInsert
→ S_ProductLaunch.initiateLaunch		 CREATE Product_Launch_Step__c ×8 Generates the full 4-lane, 8-step checklist from the hardcoded TEMPLATE. Every step's Due_Date__c = Launch_Date__c − offset; At_Risk__c computed immediately if already overdue. Owner__c defaults to the launch's creator (placeholder, no persona logic).
Product_Launch__c
after update (Launch_Date__c changed)		 ProductLaunchTriggerService.afterUpdate
→ S_ProductLaunch.handleLaunchDateChange		 UPDATE Product_Launch_Step__c (all children) Re-derives every step's Due_Date__c from its fixed Offset_Days__c against the new date, and re-evaluates At_Risk__c. Never auto-extends for late supplier changes — only recomputes.
Product_Launch_Step__c
after insert / update / delete		 ProductLaunchStepTriggerService.*
→ S_ProductLaunch.recalculateReadiness		 UPDATE Product_Launch__c (parent) Re-queries all steps for the parent (not incremental), tallies per lane, and rewrites Purchasing_Ready__c / Warehouse_Ready__c / POS_Ready__c / Sales_Activation_Ready__c, Readiness_Percent__c, At_Risk__c, and Status__c. A lane with 0 steps is never "ready" (needs ≥1 step, 0 incomplete) — this is what makes a deleted lane show as not-ready with a lower total step count in the % denominator.
LWC load
productLaunchPlan		 ProductLaunchController.getLaunchPlan PULL Product_Launch__c, Product_Launch_Step__c, Item__r.Name, Owner__r.Name Cacheable read. Assembles the 4-lane view the board renders — no writes.
LWC load
productLaunchPlan		 ProductLaunchController.buildContextSignals PULL Inventory__c, Purchase_Order_Item__c, Promotion__c Three independent read-only queries by Item__c, one per applicable lane (POS Material has none wired). Purely informational — never feeds back into the ready flags.
Inline edit
(status dropdown / Reassign)		 ProductLaunchController.updateStep UPDATE Product_Launch_Step__c (single row) Writes Status__c and/or Owner__c on one step. This is what re-triggers the step trigger above — one inline edit cascades into a full parent-readiness recompute.
"+ New Task" (per-lane, added post-review) ProductLaunchController.createStep CREATE Product_Launch_Step__c (single row) Ad-hoc step outside the template. Re-queries the launch's Launch_Date__c and back-derives an Offset_Days__c from the given due date, so this step reflows the same as templated ones if the launch date later changes. Also re-triggers the step trigger → parent readiness recompute.
"Delete" (per-step, added post-review) ProductLaunchController.deleteStep DELETE Product_Launch_Step__c (single row) Removes a step entirely. afterDelete on the step trigger still fires recalculateReadiness — a lane that drops to 0 steps is never "ready" (see note below), same behavior as the manually-emptied Sales Activation lane on demo record PL-00000009.
Save on any Product_Launch_Step__c Owner_Required validation rule GATE Product_Launch_Step__c Blocks save if Owner__c is blank. Not a mover — a guard rail.
The cascade in one line: LWC edit → updateStep writes one step → step trigger fires → recalculateReadiness re-reads all sibling steps → rewrites the parent's rollups → LWC's cacheable read reflects the new state on next load/refresh.
Known gap: the context-signal pulls (Inventory/PO/Promotion) and the checklist steps are entirely decoupled — completing a step never creates/updates the real PO, inventory, or promotion record it references, and vice versa. They're two independent signals meant to cross-check each other, not synced.
Post-review additions (not yet committed): ad-hoc task create/delete per lane, one-per-row collapsible layout, and Offset_Days__c now surfaced next to each step's due date (e.g. Due 07/06/26 (-7d)) — previously computed but never displayed. No permission-set changes were needed: Lane__c/Step_Label__c/Offset_Days__c/Status__c are all required fields, which Salesforce makes implicitly accessible to anyone with object create/edit rights (already granted) — explicit FLS entries for required fields aren't even deployable.
