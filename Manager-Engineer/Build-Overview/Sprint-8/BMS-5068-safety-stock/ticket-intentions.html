BMS-5068 · Safety Stock Controls · epic walkthrough

What every ticket in this epic is actually for

Six tickets, one branch, one PR (#442) — here's the intention behind each one, in plain language, and how they connect.

🧭 The throughline: BMS-4217 makes the system actually use a target buffer when sizing orders. BMS-5636 lets planners raise that buffer for a whole supplier, not just one SKU, with a real lifecycle. BMS-5638 + BMS-5639 make sure every generated order remembers which buffer decided its size, and warns planners before a buffer lapses. BMS-5640 gives planners a screen to do all of this instead of raw record pages. BMS-5641 gives managers a report to review it after the fact.
  1. Planner raises a buffer (5636) →
  2. Replenishment sizing reacts to it (4217) →
  3. Generated tasks freeze what target/source they used (5638/5639) →
  4. Planner manages it all from one screen (5640) →
  5. Managers audit the history (5641)

BMS-4217 — DOH-driven replenishment order sizing

✅ Built
Why it exists: before this ticket, a SKU's "Target DOH" (days of inventory it should carry) was just a number sitting on a record — nothing downstream actually read it when deciding how much to order. Raising a buffer had zero effect on real replenishment quantities.
  • Wires the resolved Target DOH into the actual order-quantity math: targetCases = targetDOH × daily velocity ÷ units-per-case, rounded to layer/pallet.
  • Flag-guarded — existing behavior is unchanged for SKUs that aren't configured, so nothing breaks for products without a target set.
  • This is the ticket that makes every other ticket in this epic matter — without it, an override is just a note; with it, an override changes what actually gets ordered.

BMS-5636 — Supplier-scope overrides + Scheduled/Manually-Closed lifecycle

✅ Built
Why it exists: the original override could only target one Item × Warehouse pair. But real disruptions (a supplier's shipping delay, a seasonal ramp) affect every product from that supplier — planners had no way to raise a buffer supplier-wide without touching every SKU one at a time.
  • New Scope field: SKU (as before) or Supplier (new) — a supplier-scope override raises the target for every SKU from that supplier at once.
  • Precedence when both exist for the same item: SKU-scope wins (more specific signal beats the broader one).
  • New lifecycle: Scheduled (future-dated, activates automatically) → Active → Expired (auto, End Date passes) or Manually Closed (planner ends it early with a reason).
  • New Adjustment Type: Temporary (must have an End Date) vs Permanent (may not have one — enforced by a new validation rule, added during QA on this epic).

BMS-5638 — Freeze effective target/source on tasks + expiry notifications

✅ Built
Why it exists: two separate but related audit gaps. (1) Once BMS-4217 makes Target DOH drive real order sizes, if a planner later changes or closes the override, a task generated last week would silently look like it used today's numbers — there'd be no record of what was actually in effect when the order was sized. (2) Overrides expire silently; a planner could be caught off guard when a buffer they were relying on lapses.
  • Replenishment_Task__c gains Effective_Target_DOH__c + Resolution_Source__c — stamped once, at generation time, so a task is a permanent record of what target and which override tier (SKU / Supplier / Standard) actually drove it.
  • Configurable expiry notice (WMS_Safety_Stock_Expiry_Notice_Days CMDT, default 4 days) — the planner who created an override gets a Salesforce notification before it lapses, instead of finding out after the fact.

BMS-5639 — Resolution-source labeling on the bulk path

✅ Built
Why it exists: the audit trail from BMS-5638 is only trustworthy if every code path that generates tasks stamps it correctly. Task generation actually runs through two different routes — a single-record resolver and a bulk resolver used for larger batches — and they're separate pieces of code.
  • Ensures S_InventoryThresholds.resolveAll() (the bulk path) labels resolutionSource exactly like the single-record resolve() path does.
  • This was caught as a real regression during this epic's QA pass — the bulk path was originally missed, so tasks generated in bulk were freezing "System Default" instead of the correct source. Fixed and re-verified (48/48 Apex tests green) before merge.

BMS-5640 — Safety Stock Manager planning screen

✅ Built
Why it exists: everything above (5636/5638/5639) lives on standard Salesforce record pages and CMDT — usable, but not something a planner would want to manage day-to-day, and there was no way to see the cost of a proposed buffer before committing to it.
  • A dedicated Safety Stock Manager tab: grid of all overrides, filterable by status, with Scope/SKU/Supplier/Target DOH/Type/Status/dates/reason columns.
  • Impact preview — pick a SKU + Location, propose a Target DOH, and see the additional cases and estimated dollar value before saving anything, computed from that SKU's real velocity and case cost.
  • Close early — a standard SLDS confirm modal with a mandatory reason (replaced an initial window.prompt implementation with this modal per repo convention, mid-epic).
  • Live-verified end-to-end in a claimed dev org via Chrome DevTools, and covered by a 3-scenario Playwright spec (grid render/filter, impact preview round-trip, close-early) — both headless and headed runs pass.

BMS-5641 — Safety Stock Overrides report type

✅ Built
Why it exists: the planning screen (5640) is built for someone actively managing overrides right now. Ops managers reviewing history — what was raised, why, by whom, for how long — need a standard reporting surface they can slice, export, and share, not a live app screen.
  • New custom report type surfacing override history for audit and review outside the planning screen.
  • Known gap (documented, not silently missed): the report doesn't yet show the estimated dollar cost of active overrides — the planning screen's impact preview has that number, but only per-proposal, not as a standing report column.
