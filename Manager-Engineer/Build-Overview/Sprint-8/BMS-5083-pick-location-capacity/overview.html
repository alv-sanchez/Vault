New here? Warehouse-slotting primer (read this first)

This whole epic is about one warehouse question: for every product, which slot does it live in, and how much of it fits there? A quick tour of the words before the Salesforce jargon starts:

Pick location (a.k.a. bin / slot). A single, specific spot in the warehouse that a picker (the worker assembling an order) pulls product from — think one labeled shelf face. Capacity = how many cases of that one product physically fit in that spot. This is beverage DSD (direct-store-delivery) at Gulf Distributing, so the unit is cases (e.g. a 24-pack case of beer).

Slotting. The decision of which product goes in which location, and how much. Good slotting means pickers walk less, refills happen less often, and bins are neither jammed full nor running empty. Bad slotting is the problem this epic attacks.

Min / Max stocking levels. Two numbers per slot. Max = "don't put more than this in — it won't fit / it's unsafe." Min = "when you drop below this, send a refill (a replenishment) before you run out." Both should follow the product's physical size, so a bulky case isn't over-assigned to a tiny shelf.

"Informal knowledge → product data." Today, how much fits in each slot lives only in experienced workers' heads. "Everyone knows you can only get 8 cases of the big water on that end-cap." This epic moves that knowledge into the system as governed data — so it survives turnover, and so software can report on it.

"Reclassification Recommended." A flag the system raises when a slot's setup no longer fits the product — e.g. a SKU started selling much faster and outgrew its small shelf. It's a "please re-slot me" alert for a manager to review, not an automatic move.

🗂️ The capacity fields, in plain English

These live on Pick_Location_Assignment__c — one record per "this SKU lives in this slot." All real, on main.

FieldWhat it means
Calculated_Max_Capacity__cHow many cases the system says fit, computed from slot size ÷ case size. Set once at creation, immutable.
Max_Capacity__cThe effective max actually used. Defaults to Calculated, but a supervisor may override it.
Capacity_Override_Reason__cRequired when Max differs from Calculated. Picklist: Structural Constraint · Safety Limit · Operational Preference · Other — so overrides are auditable, not silent.
Min_Capacity__cThe refill trigger. Drop below this on-hand → replenishment fires.
Reclassification_Recommended__cCheckbox flipped by the days-on-hand (DOH) engine when a SKU's velocity outgrew its slot → "review for re-slotting."
Go deeper — how Calculated_Max_Capacity__c is derived from case volume

It's pure geometry, done in real code: E_PickLocationAssignment.calculateCapacity(itemId, locationId).

Step 1 — case volume. Each Item__c has a formula field Case_Volume__c = (Case_Length__c × Case_Width__c × Case_Height__c) ÷ 1728, in cubic feet (1728 = 12³, converting cubic inches → cubic feet).

Step 2 — slot volume. The Location__c (the bin) carries its own Cubic_Volume__c (from its width/height/depth).

Step 3 — divide and floor.

Calculated_Max_Capacity = floor( Location.Cubic_Volume__c ÷ Item.Case_Volume__c )

Floor (round down) because you can't store a fraction of a case. If either dimension is missing or zero, the code returns "Case dimensions not configured — capacity must be set manually" and the supervisor enters the number by hand. This is the "informal knowledge → product data" step: a measurement, not a memory.

Go deeper — why native Reports/Dashboards instead of a custom LWC

Everything this epic needs to show is aggregate-and-filter: % of slots over capacity, override rate grouped by reason, count of reclassification-recommended slots. Salesforce's native reporting does grouping, filtering, charts and dashboards out of the box.

Native wins here because:

  • Zero code to maintain — no JavaScript, no Apex controller, no test coverage burden.
  • Central upgrade path — the report type and a reference dashboard ship inside the managed package, so every customer org gets them on upgrade. Customers' own report instances, filters and folders stay per-org (they'd drift if hard-coded anyway).
  • Users self-serve — admins clone/tweak reports without a developer.

An LWC would be cost with no payoff: it can't be cloned by an admin, needs ongoing maintenance, and would re-implement what the platform already gives for free. You'd only reach for an LWC if you needed bespoke interactivity reporting can't express — not the case here.
