2The exact code you pasted — line by line ownership

filterEligiblePromotions(...) shared — you reuse it

S_PriceResolver.cls · ~L630–700 · authored BMS-3876, extended BMS-4144 + BMS-4145

This is not your code. It's the single, shared eligibility gate. Each branch traces to a ticket:

  • Exclusion check (excludedPromotionIds.contains) — BMS-3876.
  • Audience membership — BMS-3876 wrote the group-member half; BMS-4144 added the isOneDaySale / group-less branch (Location/Channel-scoped or company-wide one-day sales).
  • Warehouse / Channel scope — BMS-4144.
  • Chain scope (Chain_Banner__c) — BMS-4145.

Your ticket's contribution to this method was the refactor that made it shared — see the doc-comment: "Shared by resolve() (pricing) and eligiblePromotionsByItem() (discovery) so eligibility has exactly ONE implementation." That sentence is the BMS-4053 design decision: discovery can never show a promo that pricing wouldn't honor.

eligiblePromotionsByItem(...) BMS-4053

global static Map<Id, List<Promotion__c>> · the storefront discovery entry point

This is yours. Where resolve() returns one winning promo per line for pricing, this returns every eligible, scope-matched promo per item — with Promotion_Tiers__r children — for the storefront's discovery UI (card badge, "promotions on this item" modal). It deliberately does not run threshold / winnow / best-for-customer, because it isn't pricing — it's listing.

It reuses the existing plumbing end-to-end: queryItems, queryAccountGroupIds, queryExclusions, queryAccountScope, and the shared filterEligiblePromotions. The only new query is the richer SELECT below.

queryDiscoveryPromotions(...) BMS-4053

private static List<Promotion__c> · the one new SOQL the discovery API needs

Also yours. Same eligibility filters and scope-OR clause as the pricing-path queryCandidatePromotions, but with a fatter SELECT (adds Name, Description__c, Start/End_Date__c, Status__c) and the (SELECT … FROM Promotion_Tiers__r ORDER BY Min_Quantity__c ASC) subquery — so QD tier detail rides along for the listing UI without a second query.

// pricing path (BMS-3876)            // discovery path (BMS-4053)
queryCandidatePromotions(...)         queryDiscoveryPromotions(...)
  SELECT pricing-only fields            SELECT + Name, Description__c, dates, Status__c
  (no tier subquery — tiers come       + (SELECT ... FROM Promotion_Tiers__r
    from queryTiers only for QDs)           ORDER BY Min_Quantity__c ASC)

4The two paths, side by side — pricing vs. discovery

This is the single most useful mental model for your contribution: same eligibility, different purpose.

resolve() — PRICING

BMS-3876 · returns money
  • Whole cart → one winner per line
  • Runs eligibility → scope → threshold → winnow → best-for-customer
  • Cart-context qty matters (tiers)
  • Output: LineResult with finalCasePrice, the single promotionId/tierId
  • Consumed by: invoice, credit, truck, ecom cart/catalog pricing

eligiblePromotionsByItem() — DISCOVERY

BMS-4053 · returns a list to show
  • Item list → all eligible promos per item
  • Runs eligibility → scope, then stops (no threshold/winnow/pricing)
  • Quantity irrelevant — it lists what could apply
  • Output: Promotion__c records + Promotion_Tiers__r for tier display
  • Consumed by: ecom badge + item-promotions modal
Why they can't disagree: both call the same filterEligiblePromotions and the same audience/exclusion/scope queries. A promo shown in the discovery modal is guaranteed to be one the pricing path also considered — the badge never lies about a deal the cart won't honor. That guarantee is the point of the BMS-4053 refactor.
Future-state caveat (unchanged). You added a discovery read API on top of an existing pricing engine; you didn't author the waterfall, the tiering, or the one-day-sale scoping. If the promotions team revises the resolver's core contract (stacking, cart-context summing, tier semantics), your discovery API and the ecom consumption ride on top of it and will need to stay aligned — but the layering is clean: discovery delegates to the shared filter rather than duplicating eligibility.
