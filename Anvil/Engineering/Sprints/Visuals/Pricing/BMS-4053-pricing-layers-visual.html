Catalog Pricing — Layered Reference

Frontline base → Promo / Volume promotions, the seeded demo data, navigation, and the SOQL that ties it together. Org: product-card-component · Account: Customer Account 0 (seed:acct-customer-0).

1The resolution pipeline — layered in order

Read top-to-bottom. Frontline is the floor (Layer 1, always runs). Promotions sit on top (Layer 2); inside Layer 2 the tier sub-layer is QD-only and is how a Volume promo picks its discount by quantity. Exactly one thing wins — no stacking.

Layer 1 · Frontline base, always
The account's negotiated case price, chosen by a most-specific-wins cascade. Not in competition with promotions — it's the foundation every promo discounts.
Layer 2 · Promotions Promo Price Volume Price
Post-off and QD live in the same pool and fight it out per line. Priority winnow first (if set), then deepest discount. One winner.
Tier sub-layer · Volume only Volume Price
A QD promotion carries Promotion_Tier__c rows. The resolver picks the highest tier whose Min_Quantity__c ≤ the summed cart quantity. This is why Volume is quantity-gated and cart-reactive — not a static catalog value.

Storefront walk-through

  • Log in as the retailer on Customer Account 0 → Shop / catalog grid: Wave Splitter shows $69 $59 + Promo Price; Sharks Fin shows $17 (Frontline — Volume dormant at qty 1).
  • Click a card → Product page: same treatment, plus a proper Call for pricing state for unresolved items.
  • (Volume fast-follow) Cart: raise Sharks Fin to 10 → flips to $17 $14 + Volume Price.

Code reference / logic map

  • Entry: Ecom_UI_Wrappers.resolveCatalogPricing → S_PriceResolver.resolve (OHFY-OMS / priceResolver).
  • Base cascade: S_FrontLinePricing.resolve — most-specific scope wins; tie-break = newest Start_Date.
  • Promo waterfall: S_PriceResolver.resolveLine — eligibility → scope → threshold → priority winnow → best-for-customer. applicableDiscount sets tierId only on a QD win — that's what distinguishes Volume from Promo.
  • Label + strikethrough: userDataService.resolveAccountPricing stamps _basePrice / _finalPrice / _hasPromoPrice / _priceSourceLabel onto each catalog clone.
  • Render: ecomProductCard.html + ecomProductPage.html — data-testids price-source-label, base-price, resolved-price, call-for-pricing-price.
  • Enablement gate: the Ohanafy Community User profile needs read on the promotion objects (added this ticket — the PR #287-class fix), or promos silently fall back to base.

Key logic notes / gotchas

  • Two independent junctions. FLP eligibility = Account_Pricing_Group__c; Promo eligibility = Account_Promotion_Group__c. Different objects — both must exist.
  • Catalog passes qty 1, so Volume stays dormant on the grid by design — it's a cart-reactive value.
  • One winner, no stacking. Promo vs Volume compete; deepest discount wins unless Priority__c forces it.
  • NONE short-circuits — no base ⇒ no promo ⇒ Call for pricing.
  • Both seeds idempotent, keyed on External_Id__c (flpdemo: / promodemo:). Re-run safe; revert in reverse order (promo, then FLP).

Why $69 and not $65 (default) or $60 (line)?
Front-line pricing is a most-specific-wins cascade. This item has an ITEM-scoped Front_Line_Price__c row ($69), which outranks the line-level and item-default rungs. The account sees that row only because it belongs to Retail Tier 1 via Account_Pricing_Group__c, and the row is scoped to its warehouse. Its Default_Case_Price__c is $65 — that's the fallback used only if no FLP row resolves.
Why −$10 applies
The account is in Promo Demo Group via Account_Promotion_Group__c (the audience junction). A Post-off Promotion__c scoped to this exact item, Active and in-date, offers $10 off. It wins (only candidate), discount applied to the $69 base. Because it's Post-off (not QD), promotionTierId stays null → the label is "Promo Price", not "Volume Price".

  1. Item__c attributes (scope keys: Item_Type, Item_Line, Supplier, Packaging)
  2. S_FrontLinePricing.resolve()  →  picks the ITEM row  →  $69 base   (3 SOQL inside)

6What's implemented — component hierarchy & what gets pulled

The card is presentational. Two backend streams feed it: the pricing stream (Sections 1–5) resolves money, and a field-set stream makes its extra data points admin-configurable with no code. ecomShop hands each card a fully-decorated item; the card just renders.

     │  passes one decorated item  +  display-fields
     ▼

     ├─ image · stock badge          ← Quantity_Available__c  (servicing warehouse only)

What gets pulled, in one line: the card receives an item whose price is already resolved (FLP + promo) and stamped, plus the admin-chosen field-set values — and renders. Lookup fields can't render in a field set, so related-object data (brand / flavor) must be exposed as a formula field on Item first.
