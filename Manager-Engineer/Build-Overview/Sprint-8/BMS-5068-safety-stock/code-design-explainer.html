Safety Stock Controls — how the code actually works

Read top-to-bottom once. The quiz cards (🧠) and analogies are the point — don't skip them; recalling is what wires it in.

🎯 The one mental model — hold onto this:
It's a thermostat for inventory. A planner sets a target ("keep 16 days of stock"). One part of the system decides what the target is right now (the resolver), another acts on it when reordering (order-sizing), and a nightly caretaker flips overrides on/off by date and warns you before they lapse (the batch + notifier). Everything else is detail hanging off those three jobs.
🌡️ Why "thermostat" is the right anchor
A thermostat doesn't heat the room — it holds a target and tells the furnace how hard to work. Same here: an override is you turning the dial ("hold 16 days for this SKU"). The resolver reads the dial. The replenishment engine is the furnace — it orders enough to hit the target. The nightly batch is the programmable timer that turns the dial up on schedule and back down when the season ends. Keep picturing the dial.

1 Meet the cast (6 players)

Before the flow, learn who does what. Each has one job. Colors repeat throughout the doc — that's deliberate (your brain tags them by hue).

The record — the "dial"
SKU_Override__c
A row that says "hold this target for this SKU (or supplier), from this date to that date, because ." Has a Scope (SKU or Supplier), a status lifecycle, and an audit trail.
The decider — "what's the target NOW?"
S_InventoryThresholds.resolve()
Given a SKU + location (+ maybe supplier), returns the one effective target after weighing all the overrides and baselines in a fixed priority order. Also stamps which tier won (resolutionSource).
The furnace — "how many to order"
S_ReplenishmentOrderSizing
Turns the target into a case count: targetDOH × daily velocity ÷ units-per-case, rounded to a layer/pallet, capped at bin capacity. Flag-guarded: un-configured SKUs are sized the old way.
The caretaker — runs nightly
BA_SKUOverride_ExpirationProcessor
Once a night: turns Scheduled → Active when a start date arrives, Active → Expired when an end date passes, supersedes the old override a replacement is taking over from, and triggers the warnings.
The messenger
S_SafetyStockNotifier
Sends the bell notification: "your override expires in N days" (approaching) and "your override expired" — to the person who created it.
The cockpit
safetyStockManager (LWC)
The screen: list overrides, filter by status, preview the cost of a proposed target before saving, and close one early. Talks to Apex through WMS_UI_Wrappers.
Mnemonic to lock the cast: "D-D-F-C-M-C" → Dial (record), Decider (resolver), Furnace (sizing), Caretaker (batch), Messenger (notifier), Cockpit (LWC). Say it once out loud. Two D's and two C's — the pairs make it easy.
Quick recall — cover the cast above and answer:
Q: Which player decides the target, and which one acts on it?
A: S_InventoryThresholds.resolve() decides; S_ReplenishmentOrderSizing acts. (Decider vs Furnace — never the same class. This separation is the whole design.)

2 The decider: how one target wins

Multiple things can have an opinion about a SKU's target at once — a SKU-specific override, a supplier-wide override, warehouse baselines. The resolver walks a fixed priority ladder and returns the first match. Most specific wins.

1
SKU-scope override — "for exactly this item at this warehouse" most specific → wins if present
2
Supplier-scope override — "for everything from this supplier" the BMS-5068 addition
3
Supplier + warehouse baseline threshold
4
Warehouse baseline threshold
5
Supplier baseline threshold
6
Nothing configured → returns null → callers fall back to their old behavior
Why a ladder instead of "add them up"? Buffers aren't additive — you want one answer, and the most specific instruction should win (a rule about one SKU beats a blanket rule about its supplier). The resolver returns a resolutionSource label — "SKU Override", "Supplier Override", or "Standard" — so every downstream number can say why it is what it is.
🎟️ Analogy: airport boarding groups
First class boards before group 1 before group 2. The gate agent calls the highest group present and stops. The resolver is the gate agent; SKU-override is first class. It never "averages" the groups — it picks the top one standing there.
The safe-by-design bit (why existing code didn't break): the new supplier tier only activates when a caller passes a accountId. Every pre-existing caller passes null, so for them the ladder behaves exactly as before. New capability, zero blast radius.
Recall — a SKU has BOTH a SKU-override (16 days) and a supplier-override (18 days) active. What target does the resolver return, and what's the source label?
A: 16 days, source "SKU Override". Rung 1 beats rung 2 — most specific wins, no averaging.

3 The furnace: target → cases to order

This is the piece that makes an override matter (ticket BMS-4217). Before it, the target was just a number nobody read. Now the replenishment engine sizes the order to hit it.

target cases = round( Target DOH × daily velocity ÷ units-per-case )
…then rounded up to a full layer/pallet, then capped at what the bin can hold. Order = target − what's already there.
🍞 Analogy: stocking a bakery shelf for a long weekend
"I want 3 days of bread" (Target DOH). "We sell 40 loaves a day" (velocity). "Bread comes 8 to a tray" (units-per-case). So: 3 × 40 ÷ 8 = 15 trays. You can't order half a tray, and the shelf only fits 20 — that's the rounding + capacity cap. Raising the target to 5 days ⇒ order more trays. That's the whole feature in one sentence.
Why "flag-guarded" + "additive"? A SKU with no configured target or no velocity data is sized exactly the old way (fill-to-capacity). The DOH math only kicks in when both a target and velocity exist. So turning this on can't regress an un-configured SKU — it only ever adds smarter sizing where the data supports it.
The subtle flag — dohDriven: a task records whether DOH drove its size. If the target's already met → dohDriven=false (DOH didn't order anything). If DOH computed a number but the bin was full → SizingResult(0, true): 0 cases but dohDriven=true, because DOH did decide — capacity just capped it. "0 cases" and "DOH ran" aren't contradictory.

4 The photograph: freezing the decision on the task

📸 Analogy: a receipt, not a live price tag
When a store rings you up, the receipt shows the price at that moment — even if the price changes tomorrow, your receipt doesn't. Every generated Replenishment_Task__c takes a photograph: Effective_Target_DOH__c and Resolution_Source__c are stamped once, at creation. Change or close the override later and old tasks still truthfully show what drove them.
Why it matters (BMS-5639): without the freeze, a task generated last week would look — in hindsight — like it used today's numbers. And there are two code paths that make tasks (the nightly scheduled path and the real-time event path) — both must stamp the photo, or a task's history depends on which door it came through. The review caught the event path missing it; it's fixed.

5 The caretaker: the nightly batch's 3 jobs

One batch, run once a night, does three things in a strict order. Picture a night-shift caretaker walking the building.

① start()
gather who's due
→
② execute()
flip statuses + supersede
→
③ finish()
warn what's expiring soon

① start() — "who needs attention tonight?"

Queries two groups: Active overrides whose End Date has passed (time to expire), and Scheduled overrides whose Start Date has arrived (time to activate).

🕐 Why it must run 1–3 AM, not before midnight: the filter is End_Date < TODAY. A record ending "today" is only eligible once the clock rolls to tomorrow. Run it at 11 PM and you'd leave expired buffers active an extra day. (This is a real gotcha baked into the setup doc.)

② execute() — flip the switches

  • Scheduled → Active (its window is still open), or straight to Expired if the whole window already passed.
  • Active → Expired for the ones past their end date.
  • Supersede the incumbent: when a Scheduled replacement activates, the old Active override for the same key is flipped to Superseded in the same save.
Why supersede matters (the blocker-adjacent bug the review caught): there's a rule — only one Active override per SKU+location. If the batch activated the replacement without retiring the incumbent, the rule would reject it and (because the save is best-effort) it would fail silently — the planner's scheduled replacement just never turns on. Superseding the old one in the same breath makes it a clean hand-off.

③ finish() — the courtesy heads-up

After the flips, it finds Active overrides whose end date is within the notice window (a CMDT, default 4 days) and hands them to the messenger. Runs after the transitions so it never warns about something it just expired.

Two access-mode details the review tightened: both the transition writes and the finish() read now run in SYSTEM_MODE with a "rule 4 — background job" citation. Otherwise a scheduling user without special permissions would silently get zero rows and the notifications would quietly never fire.
Recall — why does the batch expire overrides in the early morning and not at 11 PM?
A: The query is End_Date < TODAY. An override ending "today" only qualifies once the clock passes midnight into the next day. Running pre-midnight skips them, leaving buffers active one extra day.
Recall — a planner schedules a replacement override. The batch activates it but the old one is still Active. What goes wrong without the supersede step?
A: The "one Active per SKU+location" uniqueness rule rejects the activation, and because the batch save is best-effort (allOrNone=false) it fails silently — the replacement never turns on and the planner sees the old target persist. Superseding the incumbent in the same DML prevents this.

6 The messenger: notifications that scale

Sends the bell alert to the override's creator. Two flavors: approaching ("expires in N days") and expired.

The trap the review caught: Salesforce caps how many custom notifications you can send per transaction. The first version sent one per override — a big nightly batch would hit the cap and silently drop the rest. Fix: group by recipient — one aggregated notification per person ("you have 3 overrides expiring soon"), so the count scales with people, not records. Plus a single log line if any get dropped, so a silent failure becomes visible.
📮 Analogy: one envelope per person, not one per bill
If you owe someone three things, you send them one letter listing all three — not three separate envelopes. Cheaper, and you won't run out of stamps (the send cap).

7 Follow one override through its whole life

This narrative ties every player together. Picture the planner "Dana" raising a buffer for Red Bull before a summer promo.

Mon — Dana creates it (via the cockpit or a record page)
A SKU_Override__c: Scope=Supplier, Target=18 days, Start=next Mon, End=+30 days, reason="summer promo." Status starts Scheduled. First she hits Preview — the LWC asks the controller "what would 18 days cost?" → sees "+240 cases, ~$7,200" before saving.
Next Mon 1:30 AM — the caretaker activates it
The nightly batch sees Start Date arrived → flips Scheduled → Active, and supersedes any prior active Red Bull override.
Tue onward — the furnace reacts
Replenishment runs. The resolver now returns 18 days (source "Supplier Override"). Order-sizing orders more cases to hit it. Each task photographs "18 / Supplier Override."
Day 26 — the heads-up
Within the 4-day window, finish() hands it to the messenger → Dana's bell: "expires in 4 days. Extend, close early, or let it expire."
Day 30 — it retires itself
End date passes → batch flips Active → Expired. Red Bull reverts to its standard target automatically. Dana gets the "expired" note. No scramble, no forgotten buffer.
Alternate ending — Dana closes it early: from the cockpit's row action she clicks Close early, a modal demands a reason, and it flips to Manually Closed with who/when/why stamped. Same revert, just planner-initiated.

9 Why the code is split this way (the "aha")

The splitWhy it exists
Decider ≠ Furnace
(resolver vs order-sizing)		"What's the target" is a different question from "how many to order." Keeping them apart means the preview screen can ask the decider without ordering anything, and order-sizing can be tested on pure numbers.
Record ≠ Caretaker
(SKU_Override__c vs the batch)		The record just states intent. The batch enforces the calendar. A planner sets a date and forgets it; the caretaker makes the date real. Time-based state changes belong in a scheduled job, not in the UI.
Notification isolated from the transitionIn execute() the status flip and the notification are deliberately separate — a notification failure must never roll back the lifecycle change. (The reviewer specifically praised this.)
Freeze on the taskA live lookup would rewrite history every time an override changed. A frozen photo makes each task auditable forever.
LWC → Wrapper → ControllerLWCs can't call another package's Apex directly; WMS_UI_Wrappers is the thin bridge. The controller holds the real logic and is reusable/testable on its own.
