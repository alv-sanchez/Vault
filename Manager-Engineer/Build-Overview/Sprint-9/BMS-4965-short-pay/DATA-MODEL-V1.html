1. What v1 actually is

Per the spike, v1 gives AR four ways to resolve a short pay — Post Credit · Mark Collected · Assign to Rep · Write Off — plus AR's Confirm step that closes a rep-collected balance. Roll-to-next-invoice was pulled (it only tracked a carry-forward, it never re-billed), and its rollToNextInvoice code was removed. No new "short pay" child objects: the model extends Invoice__c/Account, adds one audit object + four config CMDTs, and reuses Credit__c and the routing objects.

Note on "Under Review": it appears in a stale LWC comment but is not a real Short_Pay_Status__c value and no code writes it — treat it as non-existent in v1.

11. Inert orphans (roll artifacts kept in metadata)

Left behind when roll was pulled from v1 — safe, documented, and intentionally not removed (they may hold historical data and anchor the deferred rebill design). Nothing in v1 code writes or reads them:

  • ORPHAN Invoice__c.Carried_Forward_Short_Pay__c — a term in the Short_Pay_Amount__c formula; always 0 in v1.
  • ORPHAN Invoice__c.Short_Pay_Rolled_To__c — lookup with no v1 writer.
  • ORPHAN Short_Pay_Status__c = 'Rolled-Forward' — picklist value with no v1 transition into it.

If Gulf ratifies true rebill, the clean path is a "Carried short pay" line item on the target invoice (so Subtotal → Total_Due actually charges it) — never editing the released Total_Due__c formula. If roll stays dead, drop these three in a dedicated cleanup.
