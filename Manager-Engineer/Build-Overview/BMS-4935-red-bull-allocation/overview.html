Domain primer — what this ticket is actually about

Gulf Distributing is a beverage distributor: it buys drinks from suppliers (Red Bull, beer brands, etc.) and trucks them to bars, gas stations and grocery stores. That trucks-to-store model is called DSD — Direct Store Delivery: the distributor's own drivers stock the store shelf directly, instead of shipping to a retailer's warehouse. Gulf runs 5 warehouses across Florida and Alabama (Milton FL; Montgomery, Mobile, Huntsville, McCalla AL), and each warehouse supplies the trucks for its own region.

Sometimes a supplier can't make enough product for everyone who wants it. When that happens the supplier allocates — it rations the scarce product, telling each distributor "you get exactly this many cases this week, no more." Red Bull does this weekly. They email Gulf one single number per product (e.g. "1,000 cases of Red Bull 12oz this week"). That one number is for all of Gulf — but Gulf has 5 warehouses, so a purchasing analyst has to split that 1,000 across the 5 warehouses by hand every week.

Two flavors of "allocation" matter here and they point in opposite directions:

Supplier allocation (inbound) = what Gulf is allowed to receive from a supplier. vs. Customer allocation (sell-side) = the most a customer is allowed to buy from Gulf.
This ticket is about the inbound kind. The existing Salesforce object happens to be the sell-side kind — that mismatch is the whole reason we build something new (see below).

A quick word on Salesforce naming you'll see throughout: anything ending in __c is a custom object or field ("c" = custom, built for this app); anything ending in __mdt is a Custom Metadata Type — configuration that ships inside the installed package (think "settings rows an admin can edit without a developer touching code"). Why a new object, not extend Allocation__c? (code-level) load-bearing

Allocation__c is not a neutral "list of allocations" table — it is a live order-blocking cap on the sell side. The class S_AllocationEnforcement (OHFY-OMS/.../services/allocation/S_AllocationEnforcement.cls) runs in the Invoice_Item__c before-insert / before-update trigger via enforceOnInsert() / enforceOnUpdate(). Its evaluate() method queries every Is_Active__c = TRUE, in-date-window Allocation__c matching the order's Customer__c, Sales_Rep__c, or Location__c, and if a line exceeds Allocated_Cases_Remaining__c it calls addError() — which hard-blocks the order line.

So if we loaded Red Bull's supplier (inbound) numbers into Allocation__c and put a warehouse in its Location__c field, the enforcement service's location tier would treat that supplier number as a sell cap and start rejecting real customer orders shipping from that warehouse — a production-breaking side effect. The "benefit" of reusing the object (shared automation) is exactly the automation that must never fire for inbound data.

→ Build a separate Supplier_Allocation__c. S_AllocationEnforcement never queries it, so the weekly import physically cannot trip an invoice-line block. (Note also: Item_Line__c.Supplier__c already models the supplier as a lookup to Account — so "supplier = an Account" is an established convention we reuse, not invent.)

Worked example — why a bad split causes a stockout or overstock

Red Bull emails Gulf one number: 1,000 cases of Red Bull 12oz for the week. That number covers all of Gulf. The 5 warehouses don't sell evenly — each region's real demand differs. Suppose true weekly demand looks like this, and the configured split %s match it:

WarehouseSplit %Allocated (1,000 × %)Real demandResult
Mobile, AL30%300300balanced
Montgomery, AL25%250250balanced
Huntsville, AL20%200200balanced
McCalla, AL15%150150balanced
Milton, FL10%100100balanced
Total100%1,0001,000Σ children = aggregate ✓

Now the same 1,000 split wrong by hand — the analyst fat-fingers Mobile to 150 and pushes the missing 150 onto Milton:

WarehouseGotDemandResult
Mobile, AL150300STOCKOUT — 150 cases short → trucks run dry → lost sales, angry retailers
Milton, FL250100OVERSTOCK — 150 too many → energy drinks sit, near expiry → markdown/waste

Same correct grand total (still 1,000), but the distribution is wrong — and that's what hits the shelf. The importer removes the human step: split %s live in config, the math is automatic, and the children are validated to sum back to the aggregate.

Rounding guard: 1,000 × 33.3% isn't a whole case. The splitter rounds each child and assigns the leftover remainder to the largest-% warehouse, so Σ(children) = aggregate exactly — no case is invented or lost in rounding.
How the weekly re-import stays clean — idempotent upsert & External Id

The import runs every week, and an analyst might re-run it (corrected file, accidental double-send). If each run blindly inserted rows, week 2 would create a second full set of duplicates. Instead each row carries a deterministic composite External Id:

redbull:{week}:{itemExtId}:{warehouseCode}
e.g.  redbull:2026-W26:RB12OZ:MOBILE-AL

Because that key is built from stable inputs, the same supplier/SKU/week/warehouse always produces the same key. The write goes through DmlService.doUpsert(rows, Supplier_Allocation__c.External_Id__c) — Salesforce matches on the External Id and updates the existing row instead of inserting a new one. Re-running the same week is therefore a no-op on row count: idempotent. (Raw DML is a repo PR blocker — everything goes through DmlService.)

Why "config-driven" means we could build before the real file arrived

Red Bull's exact file format (column labels, order, week encoding, CSV vs XLSX) is partner-gated and wasn't in hand. Rather than hard-code one guess and rebuild later, the parser reads its instructions from Custom Metadata — the same proven pattern the repo already uses for LotIdentifierParser + Lot_Identifier_Format__mdt ("parse-spec-in-CMDT").

Allocation_Import_Mapping__mdt — one row per source column: source label/index → target field, data type, required?, transform (Trim / Upper / StripNonNumeric / ParseWeek), feed ("RedBull"). Change a column name? Edit a metadata row, no deploy.

Warehouse_Allocation_Split__mdt — one row per warehouse: Warehouse_Code__c, Percent__c, optional Item_Key__c (blank = the default split set; set = a per-SKU override), Is_Active__c. The active default set must sum to 100, and each override set must sum to 100 — else the file is rejected. When Gulf's real warehouse codes and percentages land, they're config edits, not code.

🧱 What was built

  • Supplier_Allocation__c (new custom object) — Supplier__c (lookup → Account), Item__c (the SKU), Location__c (the warehouse, Type__c = "Warehouse"), Allocated_Case_Amount__c, Allocation_Week__c, unique External_Id__c, Is_Active__c, Parent_Supplier_Allocation__c (self-lookup: parent = supplier total, children = the 5 warehouse rows).
  • Allocation_Import_Mapping__mdt (CMDT) — one row per source column → target field / data type / required / transform / feed.
  • Warehouse_Allocation_Split__mdt (CMDT) — Warehouse_Code__c, Percent__c, Item_Key__c (default set / per-SKU override), Is_Active__c; active set must sum to 100.
  • Apex importer — S_AllocationImportConfig (loads the CMDT config), S_AllocationCsvParser (parses + validates rows), S_WarehouseAllocationSplit (explodes aggregate → 5 children with remainder guard), E_SupplierAllocationImport (the orchestrating entry point) + _T tests.

⚠️ Risk / guardrail

  • The biggest risk is contaminating invoice-item enforcement: any active, in-window Allocation__c row that references a warehouse becomes a live order-blocking cap via S_AllocationEnforcement. Keeping supplier data in the separate Supplier_Allocation__c object guarantees the import can never trip an invoice-line block.
