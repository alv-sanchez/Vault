Lesson 0001 · How /code-review Works

What /code-review Solves — and Why It's Built the Way It Is

You ran a review on PR #503 (BMS-3768) earlier — flagged an out-of-scope ci.yml hunk, then caught a legitimate PLTFM file deletion that slipped past a "cleanup" commit. This lesson explains why the tool that produces reviews like that is structured the way it is — the problem it solves, why that problem matters in the SDLC, and why its output looks the way it does.

1. The problem it solves

Unstructured human code review has three failure modes, all well documented:

  • Fatigue. Per the SmartBear/Cisco peer-review study, defect-detection effectiveness drops sharply once a reviewer exceeds roughly 200–400 lines per hour, and again past about 60 minutes of continuous review. (source) PR #503 alone was 148 files at one point — well past that threshold for a single sitting.
  • Inconsistency. What one reviewer flags as a blocker, another waves through — there's no shared, written bar.
  • Single-pass bias. A human reviewer reads once, forms a theory, and tends to confirm it rather than actively hunt for a reason they're wrong.
Grounded in this repo CODE-REVIEW.md exists specifically to fix the "inconsistency" failure mode — it's a single written bar (hard rules + severity definitions) that every review, human or agent-assisted, is judged against.

2. Why this matters in the SDLC

The cost-of-change curve is the whole argument: a defect caught at review time costs a comment and a re-push. The same defect caught in production costs an incident, a hotfix, and — in this repo specifically — potentially a broken nightly snapshot build that takes the whole CI org pool down with it (see: repo Hard Constraint #7 on the ohfy__ namespace prefix bug, and the exact WMS_UI_Wrappers.cls blocker that got caught on PR #503's first review pass).

The later a defect is caught, the more expensive it is to fix — that's the entire reason review exists as a gate at all, rather than trusting tests and CI alone.

3. How it actually runs — the pipeline

1 · GatherTicket + diff. What does the PR claim to do?
→
2 · FindMultiple independent "angles" scan in parallel — bugs, removed behavior, cross-file breakage, reuse, simplification.
→
3 · VerifyEach candidate finding gets a separate adversarial pass whose only job is to try to refute it.
→
4 · OutputSeverity-labeled, file:line-cited, in a fixed section order.

Step 3 is the direct fix for "single-pass bias" above — a finder that talks itself into a false positive gets checked by a separate pass whose entire incentive is to prove it wrong, and returns exactly one of CONFIRMED, PLAUSIBLE, or REFUTED. Nothing reaches you unverified. (Google's own reviewer guidance makes the same point about human reviewers: don't approve on a first-pass gut feeling.)

4. Why the output is shaped the way it is (the psychology)

This is the part that's easy to miss: the output format isn't a style choice, it's fighting specific cognitive failure modes.

Design choiceWhat it's fighting
Fixed section order (Bugs → Silent Failures → Dead Branches → ... → Kudos)Cognitive load. A wall of undifferentiated prose forces the reader to build their own mental filing system every time; a fixed structure means they already know where to look.
Three-tier severity: BLOCKER / WARNING / SUGGESTION — "one finding, one severity," no hedgingAlert fatigue. If everything is flagged with equal urgency, the reader stops trusting the flags at all (see: the "cry wolf" effect in alerting design generally).
Every finding cited as file:lineUnverifiable authority. A claim you can't check is a claim you either blindly trust or blindly ignore — citing the exact line lets the reader verify in seconds instead of taking it on faith.
"Ask, Don't Assume" — uncertain findings become questions, not confident-sounding guessesFalse certainty. A wrong, confidently-worded blocker is worse than an honest question — it burns trust and wastes the author's time pushing back on a phantom.
Kudos section, specific and line-citedDefensiveness. A review that's 100% criticism reads as an attack; calling out something done well (specifically, not generically) keeps the author receptive to the criticism that follows.

You already felt some of this first-hand: when you posted the review comment on PR #503's ci.yml hunk, you led with "overall this is a solid feature" before the critical finding — that's the Kudos principle, applied instinctively.

Your memory hook

The pipeline
Gather → Find → Verify → Output

Say it as one phrase: "Good Finders Verify Output." Ticket context in, many independent eyes hunting, one skeptic checking each hit, one fixed-shape report out.

Why the output can be trusted — F.A.C.T.
Focus first · Ask, don't assume · Cite file:line · Tier by severity

High-impact decisions get read before nits. Uncertainty becomes a question, not a guess. Every claim points at real code. Every finding gets exactly one severity — no hedging.

If someone asks you "what's actually in a /code-review output": it's Bugs, Silent Failures, Dead Branches, Dead Code, Debug Statements, Naming Violations, Questions, Kudos, Summary — but you don't need to memorize that list. Say "G-F-V-O pipeline, F.A.C.T. output" and you can reconstruct the reasoning for any section from there. The full section list lives in the cheat sheet for when you need the exact names.
