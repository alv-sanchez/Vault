When to Skip the AI Review Don't burn a $2-4 review on changes that don't need it

Skip AI Review

✕ Metadata-only PRs — field-meta.xml, permission sets, layouts, profiles. CI validates deploy; no logic to review.
✕ Version bumps only — sfdx-project.json version increments, package.json dep bumps. Nothing to catch.
✕ Documentation-only — README, CLAUDE.md updates, .md files. Prettier handles formatting.
✕ Org-metadata snapshot sync — managed/scratch mirror updates. Prefix rules are the only concern, and those are in REVIEW.md skip list anyway.
✕ Namespace removal (ohfy__) — stripping managed namespace prefixes from metadata. Mechanical find-and-replace, no logic to analyze.
✕ File reorganization — moving files between folders/packages. No code changed, just structure. Left to the discretion of the PR creator.
✕ Trivial one-liners — typo fixes, label changes, single-line config edits. Human glance is enough.

Always Run AI Review

✓ Any Apex change — classes, triggers, trigger services. Governor limits, security, conventions, cross-file impact.
✓ Any LWC change — JS, HTML, CSS. XSS, reactive thrashing, promise handling, @wire misuse.
✓ Cross-package changes — anything touching DTOs, ServiceLocator wiring, or shared interfaces. High regression risk.
✓ Trigger service modifications — cascade risk across all sObject operations. Always needs cross-file check.
✓ Security-sensitive code — @AuraEnabled endpoints, SYSTEM_MODE usage, CRUD/FLS-adjacent changes.

How to Trigger the Review Options for controlling when the CI/CD review fires

Recommended

@claude Comment

Comment @claude on the PR when you're ready for a review. Runs once, on demand. Cancellable mid-run.

on:
  issue_comment:
    types: [created]
if: contains(comment.body, '@claude')
~$2-4 per review, only when asked

GitHub Label

Add a claude-review label to the PR. Workflow checks for the label before running.

on:
  pull_request:
    types: [labeled]
if: contains(labels.*.name, 'claude-review')
Visual indicator on the PR that review was requested

PR Template Checkbox

Add a checkbox to the PR template. Workflow parses the body and only runs if checked.

# In PR template:
- [x] Request Claude review
# Workflow checks body
Opt-in at PR creation time, part of the PR flow

Draft → Ready for Review

Review fires automatically when you mark a draft PR as "Ready for review." One review per PR, no accidental re-triggers on push.

on:
  pull_request:
    types: [ready_for_review]
Best if team already uses draft PR workflow

Avoid: On Every Push

Triggering on every synchronize event means every commit fires a full review. 5 pushes to a PR = 5 reviews = $10-20+. This is where the "$20/PR" horror stories come from.

on:
  pull_request:
    types: [opened, synchronize]
# ^ DO NOT use synchronize
$2-4 per push × N pushes = cost blowout

Shared Rulebook REVIEW.md governs both local and CI reviews

REVIEW.md
Severity Definitions
  • Important: Logic bugs, data loss, governor limits, security vulnerabilities, broken QueryService/DmlService/Logger patterns, SYSTEM_MODE without rule citation
  • Nit: Style, naming, minor refactoring. Max 8 per review.
Always Check (Salesforce-Specific)
  • No raw SOQL/DML in non-_T classes (must use QueryService / DmlService)
  • Every catch block has Logger.getInstance().error() + flush()
  • Explicit AccessLevel.SYSTEM_MODE has rule-citing comment (rules 1/2/3/4/6)
  • DTOs crossing package + @AuraEnabled boundary are global with { get; set; }
  • org-metadata/ changes mirror both managed/ and scratch/ with correct prefix
  • No System.debug() or console.log() in production code
Skip (Already Enforced by CI)
  • Prettier formatting, ESLint violations, hex colors, Jest pass/fail, Apex test pass/fail
Do Not Report
  • Generated metadata XML boilerplate, version-bump-only changes, test-only code (_T.cls)

Cost Controls Tunable knobs inside the workflow YAML

.github/workflows/claude-review.yml
- uses: anthropics/claude-code-action@v1 with: anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }} claude_args: "--max-turns 10 --model claude-sonnet-4-6"

--max-turns (Review Depth)

Controls how many back-and-forth iterations the agent takes — reading files, inspecting the diff, posting comments. More turns = deeper analysis = higher cost.

--max-turns 5 ~30-50% cheaper
--max-turns 10 Recommended balance
--max-turns 15+ Deeper, diminishing returns

Other Levers

Trigger: @claude comment only
Review runs only when someone comments @claude on the PR. You control exactly when it fires. Avoids the "$20/PR" trap of triggering on every push (5 pushes = 5 reviews). Cancellable mid-run from Actions tab.
REVIEW.md skip rules
Exclude generated files, lockfiles, metadata XML boilerplate. Saves 10-30%.
Model selection
Sonnet 4.6 ($3/$15 per 1M tokens) is the recommended balance. Haiku is cheaper but shallower.

What Happens Each Turn --max-turns is sequential depth, not parallel agents

Each turn is one cycle: the agent thinks, reads a file from the PR diff or repo, gets the result, then thinks again. It's one agent working sequentially — going back and forth between the PR diff (what changed) and the actual repo files (full context). Cost compounds because each turn re-sends everything read in prior turns.

Why cost compounds: By turn 8, the agent's conversation includes everything it read in turns 1–7 — the full diff, CLAUDE.md, every file it opened. Each subsequent turn re-sends that growing context. A large CLAUDE.md or many changed files means more tokens accumulating per turn.

What hybrid review does NOT replace

Human judgment
Architecture decisions, UX feedback, domain logic, "should we even build this?" — still needs a human.
CI pipeline
Compile errors, test failures, Prettier formatting, deploy validation — still runs as-is. AI review is additive, not a replacement.
Pre-refinement
/polish and ticket validation happen at a different phase entirely. Hybrid review is merge-time, not planning-time.
