Billback one-per-agreement — split Billback__c from one-per-supplier

In Progress Story Priority: TBD
crawl domain:pricing-revenue-integrity gulf onsite-jun2026 tier:go-live
↗ View PR on GitHub  ·  ↗ BMS-5843 in Jira

As a Gulf Finance Controller, each supplier funding agreement should own its own Billback__c record instead of sharing one per supplier — so multi-agreement suppliers (different brands, warehouses, program types) get isolated billback tracking and reconciliation without cross-contamination. The prerequisite model decision (confirmed with Emily/Dave, 2026-07-23) is pure per-agreement grouping, not further split by warehouse; end-of-month settlement still nets to one consolidated invoice per supplier.

Acceptance Criteria

  • Billback__c has Supplier_Funding_Agreement__c lookup deployed
  • A supplier with 2 active agreements gets 2 separate Billback__c records
  • updateBillbacks accumulates to the correct per-agreement record without double-counting
  • End-of-month finalization produces one invoice per supplier (summing across agreements)
  • _T coverage ≥ 90%; multi-agreement scenario covered
Implementation Narrative

What Was Built

The billback header's identity moves from a short-lived per-invoice key (bb:{invoiceId}:{supplierId}) to a persistent per-agreement key (bb:agr:{agreementId}, with a bb:sup:{supplierId} fallback for unattributed lines) that accumulates across the agreement's lifetime. A new released Supplier_Funding_Agreement__c lookup stamps each header; the agreement is embedded in the line External_Ids so an agreement change safely re-homes a non-reparentable master-detail line via retract-old + create-new. The incentive trigger's updateBillbacks was rewritten to a single hardened pass that eliminates a real full-completions + delta double-count and routes volume accruals to the correct per-agreement header. Two downstream fixes (per-line aging, incentive relink/unlink reversal) were pulled forward from follow-up BMS-6091 during review.

Key Decisions

  1. Header keyed by agreement, not invoice — a persistent header accumulates across the agreement's lifetime; unattributed lines (account-default / 100% fallback) collect on a per-supplier fallback header. Keys are self-describing (bb:agr: / bb:sup:) so the two shapes can't collide even in principle.
  2. Agreement is embedded in the line External_Id. Because Billback_Line__c.Billback__c is a non-reparentable master-detail, an agreement change makes a NEW line (old one retracted) rather than an illegal reparent — the same pattern already used for supplier changes.
  3. Charge_Date is stamped on brand-new headers only (via a pre-resolved existing-key set) so a persistent header's aging anchor doesn't churn; aging then reads each line's own invoice date for accuracy.
  4. The legacy Incentive__c.Billback__c link stays and routes the volume accrual (Total_Cases__c), kept disjoint from the recompute path's Total_Recoverable_Amount__c rollup so a supplier's money is never counted on both.
  5. A later invoice mapping to an already-Cancelled header has its recoverable dropped but audited via Logger (header id, supplier, line count, $ total) — surfacing what the persistent key would otherwise silently swallow.
