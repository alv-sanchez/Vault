1. The one-paragraph context

A planner raises the safety-stock Target DOH ("Days of Inventory") for a SKU or supplier — meaning "keep more on hand." The buffer math is done and correct. The open question is which order quantity that target should move, because "keep more on hand" has two legitimate meanings that live in two different parts of the system:
  • Option A — pick-face replenishment: move more cases from bulk storage to the front-of-shelf pick bin, using stock we already own. (This is what shipped.)
  • Option B — inbound PO sizing: buy more cases from the supplier on the next purchase order. (Not built — no code consumes DOH here yet.)
The epic's own wording ("supplier lead-time variability, seasonal demand swings") sounds like Option B. But the only existing DOH consumer in the codebase was Option A, so that's what BMS-4217 wired into. Hence the fork.

2. What's actually in the code today

Option A — Pick-face replenishment ✅ BUILT

Refills the pick bin from bulk stock in the same warehouse. DOH sizing is flag-guarded and additive.

DOH's role here: keep the bin from going dry mid-shift.

Option B — Inbound PO sizing not built

Decides how many cases to buy from the supplier on the next PO. Protects against a slow supplier / seasonal demand.

OHFY-WMS/.../executables/…/E_PurchaseOrder.cls (no DOH consumer exists)

  • No code reads Target DOH on the purchasing path today — this would be net-new.
  • Would need its own velocity + lead-time model (reorder point = lead-time demand + safety buffer), not just bin-capacity fill.
  • Conceptually a different epic (purchasing), not just an extension of the replenishment task engine.

DOH's role here: reorder buffer vs supplier lead-time + demand swings.

3. The specific technical fork

BMS-5636 added a supplier-scope override (SKU_Override__c.Scope__c = 'Supplier', keyed by Account__c). S_InventoryThresholds.resolve(itemId, locationId, accountId) already accepts a supplier accountId and will return the supplier-tier target — but the replenishment engine deliberately passes null for it today. The code says so explicitly:

// OPEN (refinement): pick-face vs inbound-PO sizing — see BMS-5068.
// ... We do NOT pass a supplier accountId into resolve(): v1 grain is
// SKU+Location only, supplier-tier is deferred. The supplier id
// (pla.Item__r.Item_Line__r.Supplier__r) would be threaded in here
// when the supplier tier is switched on.
//   — E_ReplenishmentTask.cls ~L396-404

So the fork is concrete:

  • If Option A is the answer and supplier overrides should also drive pick-face sizing → thread pla.Item__r.Item_Line__r.Supplier__r.Id into the resolveAll requests so supplier-scope targets actually affect the bin. ~small, contained change in this same file.
  • If Option B is the answer → supplier-scope DOH should not touch pick-face at all; it belongs on the purchasing path (new work, likely a separate ticket/epic), and the supplier override we built is really an input to PO sizing, not replenishment.
  • If both → A's bin protection and B's buy-quantity are independent and both consume the target; needs the clearest data model (one target, two consumers).
