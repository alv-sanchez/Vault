Quick Reference · Epic BMS-5161 — Supplier Freight Cost Billbacks

ERD & Flows — the whole picture

The data model and every control flow on one page. Code-verified against the integration/bms-5161-validation worktree.

The one idea Freight billback is not a new recovery system. It is a new Type__c = 'Freight' on the already-shipped BMS-4141 Billback__c ledger, fed by two new source triggers: a completed cross-state Transfer, and a reconciled PO. Reuse the trunk; add two doors.

1. Data model — DBML

Paste into dbdiagram.io for an interactive render. All FKs verified in OHFY-Data-Model/.../objects/*/fields.

Table Account {
  Id   varchar [pk]
  Note: 'Standard. THREE roles: Billback counterparty, Transfer freight acct, PO supplier.'
}

Table Supplier_Funding_Agreement__c {
  Id                  varchar [pk]

  State__c            varchar
  Is_Active__c        boolean

Table Transfer_Group__c {                             // OHFY-WMS
  Id                             varchar [pk]
  Status__c                      varchar   // New -> In Progress -> Complete
  // ── BMS-5789 / PR #511 ──
  Freight_Cost__c                number    // Currency(18,2)
  Freight_Cost_Source__c         varchar   // Truck Builder | Manual | Import | API
  Recoverable_Freight_Account__c varchar [ref: > Account.Id]  // Lookup
  Is_Cross_State__c              boolean   // Formula: Origin state <> Dest state
}

Table Purchase_Order__c {                             // OHFY-WMS
  Id                          varchar [pk]
  Status__c                   varchar
  Supplier__c                 varchar [ref: > Account.Id]  // Master-Detail
  // ── BMS-5791 / PR #516 ──
  Supplier_Owes_Freight__c    boolean   // set at reconciliation = trigger signal
  Recoverable_Freight_Cost__c number    // Currency(18,2)
}

Table Billback__c {                                   // BMS-4141 ledger
  Id                          varchar [pk]
  Account__c                  varchar [ref: > Account.Id]  // Lookup (counterparty-generic)
  Type__c                     varchar   // Billback|Rebate|...|MDF|FREIGHT
  Status__c                   varchar
  Coverage_Percent__c         number
  Total_Recoverable_Amount__c number
  Has_Related_Claim__c        boolean   // BMS-5790 AC4 (overlap audit)
  External_Id__c              varchar [unique]  // deterministic -> idempotent upsert
}

Table Billback_Line__c {
  Id                    varchar [pk]
  Billback__c           varchar [ref: > Billback__c.Id]         // Master-Detail
  Transfer_Group__c     varchar [ref: > Transfer_Group__c.Id]   // Lookup (transfer source)
  Purchase_Order__c     varchar [ref: > Purchase_Order__c.Id]   // Lookup (PO source)
  Amount__c             number
  Recoverable_Amount__c number
  Coverage_Percent__c   number
  External_Id__c        varchar [unique]
}

An Account shows up three ways. Its funding agreement says what % is recoverable. A completed Transfer_Group__c or a reconciled Purchase_Order__c becomes a Billback__c (Type = Freight) with a Billback_Line__c pointing back at whichever source created it.

Gate: fires only on the → Complete transition (Status__c == 'Complete' && old != 'Complete') — the literal "set to complete" trigger. A billback-side error never fails the transfer save; the nightly sweep regenerates it.

The one difference from Flow A The PO path fires on the freight-owed reconciliation signal (Supplier_Owes_Freight__c set + amount/supplier present + changed), not on Status = Complete. Same end result — a freight Billback__c — different trigger point, by design (freight on a PO is discovered at reconciliation, a separate act from the PO closing).

WMS and OMS are sibling Tier-3 packages — WMS can't compile against an OMS concrete type. So the trigger resolves an interface registered in the Tier-1 Service-Locator, and OMS supplies the implementation at runtime. Same seam as the shipped DeliveryUpdaterService.
