How a Transfer Group commit gets gated end-to-end: the two entry paths that issue the status update, the trigger framework that dispatches it, the enforcement that converts unit-aware minimums to cases and blocks, and the rollback-proof audit trail that feeds reporting.

03 Inside enforceMinTransferQuantity()

Bulk-safe: two queries, no SOQL in loops. OHFY-WMS/.../triggerServices/transferGroup/TransferGroupTriggerService.cls

Filter to the commit point
Keep only groups crossing New → In Progress (old=New, new=In Progress). Empty → return early.
Query 1 — the lines
Transfer__c on the committing groups, incl. Item__r.Cases_Per_Layer__c / Cases_Per_Pallet__c. Sum cases per (group, item).
Query 2 — active thresholds
Transfer_Threshold__c where Item__c IN :items AND Is_Active__c=true. Grouped by item.
Resolve the applicable threshold
resolveApplicableThreshold() — most-specific lane wins (exact > one-sided > global); ties → strictest (highest min).
Convert minimum to cases
casesPerUnit(): Cases→1, Layers→Cases_Per_Layer, Pallets→Cases_Per_Pallet. Missing factor → skip this item (not blocked). minCases = Min_Quantity × casesPerUnit.
Check minimum
If totalCases < minCases → violation (names item, configured min in its unit + case-equiv, shortfall).
Check rounding (pallet/layer mode)
Else if Use_Pallets_And_Layers__c & Enforce_Layer_Pallet_Rounding__c → isWholeMultiple(totalCases, casesPerUnit) must hold, else violation.
Publish audit event, then throw
Any violations → EventBus.publish the Block__e events (PublishImmediately), then throw → entire transaction rolls back.

03·5 How it knows which thresholds to check — the joins

The enforcement never starts from items. It starts from the committing groups, walks down to their child Transfer__c lines (the link is the Transfer__c.Transfer_Group__c lookup), reads each line's Item__c, then pulls active thresholds keyed by those item ids and matches them to the group's lane.

Transfer_Group__c Id ← Transfer_Group__c▶1 : many Transfer__c (line) Item__c▶lookup Item__c (factors) Item__c▶+ lane match Transfer_Threshold__c
① Start: the committing groups (from Trigger context)
Compare Trigger.new vs Trigger.old; keep only groups where old Status = New and new Status = In Progress. Their Ids become the anchor.
Set<Id> groupIds = { groups crossing New → In Progress }
▼ join on Transfer__c.Transfer_Group__c = Group.Idthis lookup is HOW it reaches the related transfer items
② SOQL 1 — pull the related transfer lines (the "items")
The child Transfer__c records of those groups. Each line carries its Item__c, the moved Transfer_Quantity_Cases__c, and the item's conversion factors via the relationship.
SELECT Item__c, Item__r.Name, Item__r.Cases_Per_Layer__c, Item__r.Cases_Per_Pallet__c, Transfer_Group__c, Transfer_Quantity_Cases__c FROM Transfer__c WHERE Transfer_Group__c IN :groupIds
▼ collect line.Item__c → Set<Id> itemIds
③ SOQL 2 — pull active thresholds for exactly those items
Keyed by the item ids gathered from the lines. Inactive rows are filtered out. Result grouped into thresholdsByItem.
SELECT Item__c, Origin_Location__c, Destination_Location__c, Min_Quantity__c, Quantity_Unit__c, Enforce_Layer_Pallet_Rounding__c FROM Transfer_Threshold__c WHERE Item__c IN :itemIds AND Is_Active__c = true
▼ for each (group, item): match by laneresolveApplicableThreshold()
④ Lane match — pick the applicable threshold
Among that item's candidates, keep those whose Origin_Location__c / Destination_Location__c are null (wildcard) or equal the group's Origin_Location__c / New_Location__c. Most-specific wins; ties → strictest (highest min).
originOk = t.Origin_Location__c == null || == group.Origin_Location__c destOk = t.Destination_Location__c == null || == group.New_Location__c specificity = (originSet?1:0) + (destSet?1:0) // higher wins; tie → higher Min_Quantity
▼ compare
⑤ Convert & check (per group+item)
Sum cases for that (group, item). casesPerUnit() turns the unit into cases via the item factors (missing factor → skip). Block if totalCases < Min_Quantity × casesPerUnit, or — in pallet/layer mode with rounding on — if it isn't a whole multiple.
So "how does it know to check the related transfer items?"
  • It doesn't iterate items globally — it queries down the Transfer__c.Transfer_Group__c lookup (step ②) to get only the lines on the committing groups.
  • Each line's Item__c drives the second query (step ③) — thresholds are fetched only for items actually on the transfer.
  • The lane (group Origin / New_Location vs threshold Origin / Destination) decides which threshold applies (step ④).
  • All of it is set-based / bulk-safe — two queries total, no SOQL inside the per-group or per-item loops.

04 The rollback-proof audit trail

The clever bit: the block throws, which rolls back the whole transaction — so a normal insert of an audit row would vanish with it. A PublishImmediately platform event is delivered outside the rolling-back transaction.

enforceMinTransferQuantity detects violation(s)
↓
PUBLISH EventBus.publish( Transfer_Threshold_Block__e )
PublishImmediately → committed independently of the doomed transaction.
↓
THROW TransferGroupTriggerServiceException → rollback
Status change reverts; user sees the message.
↓ EVENT DELIVERED SEPARATELY
SUBSCRIBER TransferThresholdBlockTriggerService → TransferThresholdEventHandler
Materialises each event into a durable Transfer_Threshold_Event__c row (Block · item · configured min · attempted · shortfall).
↓
📊 Reporting source for BMS-4667
Blocked-commit counts by item / lane / warehouse; coverage gaps. Same Log__e survive-the-rollback pattern used elsewhere in the repo.

⛳ The one thing to remember
  • Enforcement is downstream of the DML, not the UI. Record-page edit (Path A) and the LWC (Path B) converge on the same UPDATE → same afterUpdate → same enforceMinTransferQuantity. There is no bypass path.
  • The minimum is unit-aware (Cases/Layers/Pallets) and converts to cases via the item's factors; rounding enforces whole-layer/pallet multiples in pallet/layer mode.
  • Hard block for v1 — no override path (deferred to phase 2). Open product question: who maintains the config records and via what surface.
  • Verify it by editing Status__c New → In Progress on a seeded test:mtq-tg-* group (the LWC path needs origin inventory the seed doesn't create).
