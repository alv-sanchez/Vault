Why this couldn't live in a Reports page

The account order-visibility panel builds custom UI for only the views a Salesforce report can't produce. This version is corrected against the actual OHFY-OMS source — the honest line is sharper than "stored vs. runtime data."

The real test

Nearly every object here is already report-enabled — promotions, invoices, inventory, deliveries all carry enableReports=true. So the dividing line is not "can a report see the data." It's: is the value a stored attribute a report can group and filter — or a computed decision, the output of a multi-step resolution that only runs in code?

Build custom only for the computed decisions: the account's resolved price, whether a promotion is eligible and why not, the restriction-resolved sellable catalog. A report can list the raw rows behind these; it cannot run the algorithm that turns them into an answer.

The rule this encodes

Custom UI is spent only on computed decisions — values that don't exist until an algorithm produces them. Everything that's a stored attribute stays native, and stays the customer's to report and configure.

Stored attribute → native / reuse

Order history · supervisor aggregate · credit & balances (reportable). Account pricing · order creation (runtime, but already shipped — reuse, don't rebuild).

Computed decision → built here

Promotion eligibility & the reason for ineligibility · most-specific-wins restriction-filtered inventory · the composed delivery banner. Outputs of a resolution — no report can select them.

What validation changed

checked against OHFY-OMS / OHFY-Data-Model source · 2026-07-24

  • Fixed Promotions no longer claim a "most-specific-wins item cascade." Each Promotion__c has one Item_Scope_Level__c; matching is flat. Resolution is priority winnow + deepest-discount tiebreak. (The specificity-cascade in that file belongs to supplier-funding floors — a different feature.)
  • Fixed Dropped "reports can't do NOT IN." Promotion_Account_Exclusion__c is a 2-field, report-enabled junction a cross-filter could reproduce alone. The real blocker is the multi-factor selection algorithm, not the anti-join.
  • Fixed Delivery downgraded ❌ → Partial. Cutoff is a stored reportable field, and deliveries are reportable via a custom multi-hop report type. Only the inline composed banner and the cadence estimate are genuinely custom.
  • Fixed Pricing / order creation recast as "reuse," not "native report." Both are runtime cascades a report can't reproduce — they're covered by shipped components, not by reporting.
  • Held Promotion eligibility, ineligibility-with-reason, and restriction-filtered inventory stand. Confirmed as genuine computed decisions in S_PriceResolver / S_MarketRestrictions — reportable data, but not a report-producible answer.
