1 · The big picture — two doors, one engine

Gulf pays freight that, by contract, a supplier owes. This feature captures that cost and turns it into a recoverable billback against the supplier — through the existing billback ledger, not a new system.

Freight arrives through two doors, and both walk into the same engine:

The model in one line Door A (cross-state transfer) and Door B (inbound PO) each capture a gross freight $ → the engine resolves the supplier's coverage % → creates a Freight billback (gross × coverage%) → AR invoices & collects it manually. 
  Door A: Transfer_Group__c  ─(Complete)──┐
                                          ├─►  ENGINE  ──►  Billback__c (Type=Freight, Accrued)
  Door B: Purchase_Order__c  ─(reconciled)┘   coverage       + Billback_Line__c  ──►  AR: Invoice → Collect
                                              × gross

Green = automatic (the system).   Red = manual (AR/finance).

2 · Flow A — Cross-state transfer

Cross-state transfer Door A
1
Capture freight (manual/assisted). On the Transfer Group, freight is entered via the "Enter Freight Cost" quick action — or auto-populated by the Truck Builder. Sets Freight_Cost__c (gross), Freight_Cost_Source__c (Manual / Truck Builder / Import / API), Recoverable_Freight_Account__c (the supplier).LWC freightCostEntry → FreightBillbackUIController.saveFreight
2
Cross-state check (auto). Is_Cross_State__c is a formula: origin state ≠ destination state. Same-state → no freight billback, ever.
3
Complete the transfer. User sets Status__c → Complete. This is the trigger.TransferGroupTriggerService.generateFreightBillbacks (afterUpdate)
4
Gate + hand-off (auto). Fires only when Status=='Complete' && old!='Complete', cross-state, with freight cost + recoverable account present → resolves the Tier-1 service via Service-Locator → enqueues the async generator.ServiceLocator → FreightBillbackService → Q_FreightBillbackGeneration → S_FreightBillbackCalculation
5
Billback created — see §4 for the math. Backstop: nightly B_FreightBillbackDetection regenerates if the trigger ever errored.

3 · Flow B — Inbound PO

Inbound PO Door B
1
PO received. A Purchase Order exists against a supplier. Freight is untouched: Supplier_Owes_Freight__c = unchecked, Recoverable_Freight_Cost__c = blank. No billback yet.
2
Reconciliation (manual, AR). AR determines the supplier owes inbound freight and edits the PO's standard fields: check Supplier_Owes_Freight__c, enter Recoverable_Freight_Cost__c (the gross carrier freight), confirm Supplier__c. No custom UI — plain field edit.
3
Gate (auto, on Save). Fires when all three are populated (eligibleNow) and at least one just changed (changed). Note: fires on a PO update, and not on Status=Complete — it's the freight signal, not PO closure.PurchaseOrderTriggerService.generateFreightBillbacks (afterUpdate)
4
Hand-off (auto). Resolves the PO service via Service-Locator → async generator.ServiceLocator → POFreightBillbackService → Q_POFreightBillbackGeneration → S_POFreightBillbackCalculation
5
Billback created — same engine, same math (§4). Backstop: nightly B_POFreightBillbackDetection.
Gotcha It's an update trigger. A PO created with the box already checked (e.g. via import) does not fire in real time — only the nightly batch catches it. Real-time creation needs the fields set via an edit to an existing PO.

4 · How the freight cost is calculated (once criteria are met)

Both doors converge here. The engine never invents the freight — it takes the captured gross and computes the recoverable share:

The engine — S_FreightBillbackCalculation / S_POFreightBillbackCalculation
1
Start with the gross. The captured freight amount (Freight_Cost__c or Recoverable_Freight_Cost__c). This is an input — the system does not calculate it.
2
Resolve coverage % (the calculated part). From the supplier's Supplier Funding Agreement, via a most-specific cascade:
  • most-specific active agreement (a brand-scoped agreement beats a supplier-wide one) →
  • else the account's default coverage →
  • else 100% (supplier owes the full freight).  An explicit 0% → no billback (distributor-funded).S_SupplierFundingAgreement.mostSpecific(...)
3
Compute recoverable. recoverable = gross × coverage%.
4
Upsert idempotently (deterministic External_Id → re-runs never duplicate): a Billback__c (Type=Freight, Account=the supplier, Status=Accrued) with a Billback_Line__c pointing back at the source (Transfer Group or PO), carrying the gross, coverage %, and recoverable.

Worked examples (live-verified):

SourceGrossCoverageRecoverable
Cross-state transfer$1,20040%$480
Inbound PO$65040%$260
Precisely Gross freight is sourced (entered, or fed by Truck Builder / receipt fees); the recoverable, coverage, billback and roll-up are all calculated from it.

5 · What the AR team does (step by step)

The system accrues the recoverable automatically; AR recovers it manually. There is no dunning or auto-collection.

AR / finance — the manual lifecycle
1
Trigger the accrual. Transfer: complete a cross-state transfer that has freight + a recoverable account. PO: reconcile — check Supplier Owes Freight and enter the gross freight. → system auto-creates the Accrued billback.
2
Review the billback. Transfer: the Supplier Freight Billback panel on the record. PO: the Billback__c record (no PO panel). Confirm supplier, coverage %, recoverable $.
3
Check for double-recovery. If Has_Related_Claim__c is flagged, a claim already exists on the same shipment — review before recovering freight on top of it. (Nightly overlap audit stamps this.)
4
Invoice the supplier → move the billback Status: Accrued → Invoiced.
5
Record payment → Invoiced → Collected (or Written_Off if uncollectable). This is where the money is "collected."
Scope Steps 4–5 are manual status changes on the standard billback lifecycle. There is no auto-invoicing, payment integration, or dunning in this epic — that would be new scope (Billback Automation, BMS-4951).

6 · Key facts that trip people up

Gross, not net

Recoverable_Freight_Cost__c / Freight_Cost__c hold the GROSS freight (the full carrier charge). Coverage % is applied downstream. Entering the supplier's net share would double-discount. (The PO field's help text has been corrected to say "gross.")

Isolated from any invoice total

Freight is not summed into any invoice / PO / transfer total. It lives only in its own supplier billback ledger — Billback__c has no invoice lookup, and freight billback lines carry no Invoice_Item__c. The only total it feeds is its own Billback__c.Total_Recoverable_Amount__c.

"Invoiced" is a billback status, not a sales invoice

The Invoiced lifecycle stage means "AR has billed the supplier" — it is not a sales Invoice record and has no invoice-total linkage.

Where the gross comes from

An input, not computed. Transfers: Truck Builder can set it (or Manual / Import / API). POs: the real freight usually already lives on an Inventory_Receipt_Fee__c (Cost_Type = Freight / Shipping / Fuel Surcharge) at receiving — today it's hand-keyed on the PO; a future receipt-fee source would pull it in automatically.
