Gulf Distributing moves product between five warehouses — Milton FL, Montgomery, Mobile, Huntsville, and McCalla AL. Two new checks now sit on that flow: one stops transfers that are too small to be worth moving, the other stops dock bookings a dock physically can't service in time. First, how a transfer works today

You can't see what these tickets add without knowing the machinery they hook into. Here's the part of the system that already existed before either ticket — the foundation both builds sit on.

A transfer has a three-step life

An inter-warehouse move is a Transfer_Group__c record (the shipment of stuff) holding many Transfer__c lines (one per item, each with a case quantity). It walks through exactly three statuses: New → In Progress → Complete. There is deliberately no "Draft" status — a point that mattered a lot, because the original ticket text assumed one existed.

The class TransferGroupTriggerService already polices that walk: it blocks moving backwards, and it won't let a group advance until it's actually picked (Is_Picked__c). The way it blocks is simple and important — it throws an exception, which rolls the whole save back. That "throw to block" pattern is exactly where the new quantity gate plugs in.

The commit moment is New → In Progress. That's when a planner stops fiddling and commits the transfer — the natural place to ask "is this move actually worth making?"

A transfer also has to get onto a dock

Separately, dock scheduling shipped back on 2026-04-29. Each appointment is a Shipment__c with one parent — a delivery, a purchase order, or a transfer group — booked onto a dock (Location__c flagged Is_Dock__c) at a time, for a duration (Shipment_Time_Minutes__c, default 60). The scheduler E_DockScheduler already prevents two appointments from overlapping the same dock (validateNoConflict), and a dashboard of LWCs (dockDashboard & friends) renders the board. The dock-fit gate extends this, without replacing any of it.

How product actually moves

Same idea as a floor map. A picker pulls cases off the pick faces onto a pallet, drops them in that route's staging lane, and once the lane is full and checked it loads through a dock door onto the truck — and that loading window is the slot the dock-fit gate protects.

Where the two gates sit on this flow: the quantity gate (BMS-4665) acts at the very start — it stops a transfer being committed at all if it's too small to be worth picking and moving. The dock-fit gate (BMS-4490) acts at step 3 — it stops a transfer being booked onto a dock whose slot can't service it in time.

01

The quantity gate

BMS-4665

Stop uneconomically small transfers at commit

Epic BMS-5162 · OHFY-Data-Model + OHFY-WMS · PR #355

The problem in plain terms

Moving product between warehouses costs handling and truck time whether you ship 3 cases or 300. Gulf wants to stop tiny, not-worth-it transfers from being committed — and for some items, to enforce that moves come in whole layers or pallets. None of that existed in code; this was greenfield logic.

Gap: what was already there to build on
Already shipped

The New → In Progress → Complete status machine and its throw-to-block guards in TransferGroupTriggerService.

Per-item case counts on Transfer__c lines, and a Use_Pallets_And_Layers__c flag on the group.

A shipped config pattern — Inventory_Threshold__c / SKU_Override__c — for "set a rule at item + location grain."

What BMS-4665 adds

Transfer_Threshold__c: the rule an admin sets — item, optional origin & destination lane, a minimum case quantity, a rounding flag, active toggle.

A new method in TransferGroupTriggerService that runs only on the commit transition.

An audit trail: Transfer_Threshold_Block__e event → Transfer_Threshold_Event__c record.

What it actually does, step by step

01
A group advances New → In Progress (and only then)
02
Read its lines; sum cases per item
03
Find the most-specific active rule for that item + lane
04
Below the minimum? (or a partial case in pallet mode) → block
05
Otherwise the commit proceeds

"Most-specific wins" means a rule for Milton→Montgomery beats a blank-lane rule for the same item; if two rules tie in specificity, the strictest minimum applies. A rule with blank origin/destination is a wildcard that covers every lane.

What data it reads — and why each query exists

// Query 1 — the items and case counts on the committing group(s).
// We need to know "how many cases of what is this transfer actually moving?"
Transfer__c → Item__c, Item__r.Name, Transfer_Group__c, Transfer_Quantity_Cases__c
  WHERE Transfer_Group__c IN :committingGroups

// Query 2 — the active rules for just those items.
// Scoped to the items we saw, so it stays cheap and bulk-safe.
Transfer_Threshold__c → Item__c, Origin_Location__c, Destination_Location__c, Min_Case_Quantity__c, Enforce_Layer_Pallet_Rounding__c
  WHERE Item__c IN :itemIds AND Is_Active__c = true

Everything after that happens in memory: cases are summed per (group, item), the lane is read from the group's Origin_Location__c and New_Location__c (the destination lookup), the right rule is resolved, and each item is checked. Two queries total, no SOQL inside loops — it stays safe even when many groups commit at once.

Why the audit uses a platform event (the non-obvious bit)

The block throws, which rolls the transaction back — so if we'd simply insert an audit record, it would be erased along with the blocked save. Instead the block is published as a PublishImmediately platform event, which is delivered outside the doomed transaction; a subscriber then writes the durable Transfer_Threshold_Event__c row. That row is what the reporting story (BMS-4667) will count.

Worked example · Gulf

Setup. An admin creates a rule: item COKE-12PK, lane Milton FL → Montgomery AL, minimum 24 cases (one layer), active.

  1. A planner builds a transfer on that lane with 3 loose cases of COKE-12PK and clicks to advance it to In Progress.
  2. The gate sums 3 cases, finds the lane rule (min 24), sees 3 < 24.
  3. It publishes a block event, then throws — the whole advance is rolled back.
⛔ Transfer Group TG-00123: item COKE-12PK moves 3 case(s) but the minimum is 24 (short by 21).

The planner stays on New, bumps the quantity to a full layer, and re-advances — clean. Meanwhile a Transfer_Threshold_Event__c row survives for the dashboard. And critically: an item with no rule is never touched — thresholds are opt-in, so today's transfers keep working until Gulf configures one.

The gate, at a glance

minimum 24 ▸ moved 3 ▸ short by 21 → BLOCKED
02

The dock-fit gate

BMS-4490

Don't book a transfer onto a dock slot it can't fit

Epic BMS-5163 · OHFY-WMS · PR #354

The problem in plain terms

Each dock door can service one operation of a fixed length — its slot. Booking a transfer that needs longer than a dock's slot means it won't actually clear in time, cascading into late route loads. The new gate catches that at booking time and points the manager at a dock that fits.

Gap: the field that means something different than the ticket assumed
The build deliberately stopped here — and it was right to

The ticket's acceptance criterion said to block a dock whose "remaining capacity cannot absorb the requested window" — wording that sounds like a cumulative daily budget (minutes used vs. minutes available per day). But the only field that exists, Dock_Capacity_Minutes__c, is a per-operation slot length — the shipped dashboard literally labels it MIN/SLOT, and the field's help says it computes one appointment's end time. There is no daily-budget field anywhere. Rather than guess, the build paused for a decision.

Decision — Option A (slot-fit): block when a single shipment's duration exceeds the dock's slot length, and suggest docks/times that fit. It's faithful to what the field actually is, needs no schema change, and still delivers the real "block + offer an alternative" behavior. The cumulative-daily-budget interpretation (Option B) would mean adding a new field to the heavily-shared Location__c object — a frozen managed-package surface — so it's parked as a deliberate phase-2 call, not a v1 default.

Slot-fit, visually

A 90-minute transfer can't sit in D1's 60-minute slot, so D1 is blocked. The system looks at sibling docks under the same warehouse and offers one whose slot is long enough — ideally one that's also free at the requested time.

How a booking is judged

01
Manager books a transfer onto a dock + time
02
Is the parent a Transfer Group? If not, skip this gate
03
Window > dock slot? → block & suggest fitting docks
04
Existing validateNoConflict overlap check
05
Fits & free → booked on Shipment__c

Two things to notice. First, it's scoped to Transfer Groups only — supplier POs and deliveries skip the capacity gate (that's the inbound-transfer vs supplier-load differentiation). Second, the old validateNoConflict stays the single authority on time overlaps; this gate runs before it, never replaces it.

What data it reads

// The target dock's slot length + which warehouse it belongs to.
Location__c → Id, Name, Dock_Capacity_Minutes__c, Parent_Location__c (LIMIT 1)

// Alternatives: sibling docks in the same warehouse with a big-enough slot.
Location__c WHERE Parent_Location__c = :parent AND Is_Dock__c = true
  AND Dock_Capacity_Minutes__c >= :requestedMinutes

// Conflict authority (already existed): appointments already on the dock.
Shipment__c → dock + dock-time fields, Shipment_Time_Minutes__c, parent name/status

If the dock has no configured capacity, or the window fits, the gate is a no-op — it never gets in the way unless there's a real mismatch.

Worked example · McCalla
  1. Dock D1 is configured at 60 MIN/SLOT. A manager tries to book a transfer that needs 90 minutes onto D1.
  2. The gate compares 90 > 60, blocks, and scans sibling docks for one that fits.
⛔ Requested window (90 min) exceeds Dock D1 slot capacity (60 min). Try: Dock D3 (120 min, open 10:00), Dock D4 (90 min).
  1. The manager re-books the same transfer onto D3 at 10:00. It clears the slot check, and validateNoConflict confirms nothing else holds D3 at that time.
✓ Booked · Transfer on Dock D3 at 10:00.

A supplier PO needing 90 minutes on the same 60-min D1 dock would not be blocked — the gate only applies to transfers.
