In one line: a retailer contact who runs several businesses signs in once and switches the active business inside the storefront — shop pricing, cart, order history, and profile all follow the selected business.

What it does

A single contact (and one ecom login) can belong to multiple businesses. The links are created in Salesforce with the native Contacts to Multiple Accounts feature; the storefront adds an account switcher in the desktop nav bar and the mobile hamburger menu.

The contact keeps one primary account; every additional business is an AccountContactRelation (indirect) record. Self-registration is unchanged — it still creates exactly one business.

Re-scoped 2026-06-11. Originally "multi-account registration." Direction changed: registration stays single-business; the multi-account capability is Salesforce-side linking plus an in-storefront switcher.

#Criterion

2Storefront switcher: switch the active business without logging out; selection persists for the session.
3Context propagation: shop/pricing, cart, order history, profile reflect the selected business.
4Single-account regression: one-account contact sees the name, no switching control.
5Registration regression: self-registration unchanged (one business, one welcome email).

How it works

Data model

A contact has one primary account (Contact.AccountId, the "direct" relation) and additional businesses as AccountContactRelation rows. That object only exists when the Contacts-to-Multiple-Accounts feature is on, and the related-accounts list is the authorization boundary for switching.

Read → switch → propagate

ecomAccountSwitcher (LWC)
   │  subscribes to userDataService
   ▼
userDataService (singleton)
   │  getRelatedAccounts() → Ecom_UI_Wrappers → AccountSwitcherController
   │                                              (server-derived from the session user)
   │  switchAccount(id) → sessionStorage → full re-init → broadcast ACCOUNT_SWITCHED
   ▼
navigationMenu + every account-scoped surface re-queries for the new account
  • AccountSwitcherController derives the contact from UserInfo.getUserId() (never trusts client input) and returns its active related accounts. References AccountContactRelation dynamically so the package still deploys where the feature is off (degrades to empty).
  • userDataService stores the related accounts, applies a valid session override over the primary account, and on switch re-runs the full init then broadcasts ACCOUNT_SWITCHED. Because every account-scoped surface already reads the account id from this one singleton, the switch propagates everywhere with no per-surface change.
  • ecomAccountSwitcher is the UI, with a header (desktop dropdown) and drawer (mobile collapsible dropdown) variant, themed from --ohfy-color-* tokens.

Customer install note

ContactsToMultipleAccounts and the Account setting are not packageable — they don't install with the ohfy managed package. A customer admin must enable "Contacts to Multiple Accounts" (Setup → Account Settings) to activate the switcher. Until then the storefront behaves single-account (switcher hidden). Add this to the install runbook.

Known constraints

Pool scratch orgs can't demo this. The shared dev-pool snapshot was built without the ContactsToMultipleAccounts feature, so AccountContactRelation never provisions on claimed orgs (the setting saves but the object is absent). Fix: add the feature to the OHFY-CICD snapshot scratch def and rebuild. Validated on a one-off scratch org created with the feature.
