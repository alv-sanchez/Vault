BMS-4053Promotions clarity

Post-off vs Volume (QD) — one object, two shapes

Both are Promotion__c records. They are not different features — a single field, Type__c, decides whether the discount is one flat cut (Post-off) or a quantity-stepped curve (Volume / QD). This page walks the difference, the three quantity scenarios, exactly what data/functions/files get pulled, and an honest note on what is & isn't built.

1They are the same object — Type__c is the only fork

A promotion is one Promotion__c row. The resolver (S_PriceResolver.applicableDiscount) branches on Type__c and nothing else to decide the discount’s shape:

                         Promotion__c  (one record)
                                │  Type__c = ?
              ┌─────────────────┴──────────────────┐
        'Post-off'                                 'QD'  (Volume)
              │                                     │
   uses the PROMO's own fields:            uses child Promotion_Tier__c rows:
     Min_Quantity__c                         each tier: Min_Quantity__c + Discount_Amount__c
     Discount_Amount__c                      → pick HIGHEST tier where cartQty ≥ tier.Min_Quantity__c
              │                                     │
   ONE flat discount once cartQty            DISCOUNT GROWS as cartQty crosses tiers
   ≥ Min_Quantity__c                                │
              │                                     │
   result.promotionTierId = null            result.promotionTierId = winning tier Id
              ▼                                     ▼
        label "Promo Price"                   label "Volume Price"
The label is just a tell, not a separate code path. The storefront shows “Volume Price” whenever the winning discount came from a tier (promotionTierId set), and “Promo Price” when it came from the promotion’s own flat fields. Same resolver, same result object (LineResult).

2The decision, in the actual code

S_PriceResolver.applicableDiscount() — the per-promo, per-line discount calc (OHFY-OMS):

if (promo.Type__c == 'QD' && tiers != null && !tiers.isEmpty()) {
    // VOLUME: walk tiers, keep the highest whose Min_Quantity ≤ cart-context qty
    for (Promotion_Tier__c tier : tiers) {
        if (cartQty < (tier.Min_Quantity__c ?? 0)) continue;     // not reached yet
        if (best == null || tierMin > bestMin) { best = tier; } // deeper tier wins
    }
    if (best == null) return null;            // no tier reached → no discount
    amount = best.Discount_Amount__c;  tierId = best.Id;          // ← "Volume Price"
} else {
    // POST-OFF (and any single-tier promo): one flat threshold + one amount
    if (cartQty < (promo.Min_Quantity__c ?? 0)) return null;     // threshold unmet → no discount
    amount = promo.Discount_Amount__c;                            // ← "Promo Price"
}
// Percent vs Dollar comes from promo.Discount_Type__c for BOTH shapes
perCase = (Discount_Type__c == 'Percent') ? casePrice * amount/100 : amount;
Threshold is cart-context quantity, not a single line: cartContextQuantities() sums every cart line whose item falls in the promo’s scope, so the same item split across two lines still tiers correctly.

Post-off — "a coupon"

  • One threshold (Min_Quantity__c), one discount (Discount_Amount__c).
  • MinQty 1 (or null) ⇒ looks unconditional.
  • MinQty > 1 ⇒ a buy-N-to-unlock deal; flat after.
  • No Promotion_Tier__c rows.
  • Label: Promo Price

Volume / QD — "a quantity ladder"

  • Discount lives in Promotion_Tier__c children.
  • Each tier = its own min qty + amount.
  • Resolver picks the deepest tier you’ve reached.
  • Below the first tier ⇒ no discount (base).
  • Label: Volume Price

5Honest reality — what IS and ISN'T built (this branch)

✓ Built & committed on this branch

  • The resolver handles BOTH Post-off and QD/Volume — S_PriceResolver.applicableDiscount has a live QD-tier branch (not a stub). Volume pricing is resolved, not just modeled. (BMS-3876 / ADR-0010, extended by BMS-4144/4145, discovery API under BMS-4053 commit 1daeccd4.)
  • The storefront calls it — Ecom_UI_Wrappers.resolveCatalogPricing / resolveCartPricing → S_PriceResolver.resolve; discovery via eligiblePromotionsByItem.
  • Data model: Promotion__c, Promotion_Tier__c, Account_Promotion_Group__c, Promotion_Account_Exclusion__c all present.
  • Demo data seeded (seed-promo-demo.apex) — a Post-off and a QD-with-tiers, which is why both resolve live in the org.

○ NOT done / out of scope here

  • BOGO promotions — deliberately deferred to BMS-3878 (no schema/branch; resolver emits no bonus lines).
  • Promotion authoring/admin UX and the broader promotion-feature stories — separate tickets, not BMS-4053.
  • End-to-end verification across many accounts/quantities — being hand-tested (the part not trusted to AI).
  • On the catalog card, Volume looks dormant because the card resolves at qty 1 (below tier mins) — it surfaces in the cart at quantity. That’s expected, not missing.
Why it felt confusing: “volume pricing data model is in but the resolver isn’t” was true at one point, but the resolver (and the storefront wiring) landed in S_PriceResolver via BMS-3876 and the BMS-4053 discovery commit. So volume does resolve today — the remaining promotion work is BOGO + authoring UX + verification, not the Post-off/Volume math.
