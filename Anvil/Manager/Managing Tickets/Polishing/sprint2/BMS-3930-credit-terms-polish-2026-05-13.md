### Contradicted — fix before refinement

#### 1. `Payment_Status__c` picklist values don't match the ACs **(HIGH IMPACT)**

- **Ticket says (AC2, AC3):** picklist values are `Open / Past Due / Partially Paid / Paid`; AC2 filters `Payment_Status__c != 'Paid'`.
- **Code shows:** `OHFY-Data-Model/force-app/main/default/objects/Invoice__c/fields/Payment_Status__c.field-meta.xml` — actual values are **`Not Paid, Paid, Partially Paid, Failed`**.
- **Assessment:** Contradicted. `Open` and `Past Due` are not stored picklist values today. `Past Due` is naturally a *derived* state (`Payment_Due_Date__c < TODAY() AND Payment_Status__c != 'Paid'`) — it does not belong on a picklist. AC2's filter `!= 'Paid'` would have to read `!= 'Paid' AND != 'Failed'` (otherwise a charge-failed invoice still drains the outstanding balance, which is also a valid debate).
- **Fix:** rewrite AC2/AC3 against the real picklist, and introduce `Is_Past_Due__c` as a formula field or a derived view-layer flag — not a picklist extension.
- 

#### 2. `Due_Date__c` field name is wrong

- **Ticket says (AC3):** invoice row displays `Due_Date__c`.
- **Code shows:** field is `Payment_Due_Date__c`.
- **Fix:** rename in AC3.

#### 3. "Warehouse" relationship on `Invoice__c` does not exist

- **Ticket says (AC3, AC6):** "originating Warehouse name" per invoice; AC6 references Milton FL / Mobile AL as "warehouse entities."
- **Code shows:** `Invoice__c` has `Fulfillment_Location__c` → `Location__c`. There is **no** `Warehouse__c` object in `OHFY-Data-Model`. `Entity__c` is a separate object — visible as `Entity__c` lookups on `Receipt__c` and elsewhere. So the ticket is conflating **Location**, **Entity**, and **Warehouse** — three distinct concepts in this data model.
- **Fix:** make a deliberate call — is per-credit-profile keyed off `Entity__c` (Gulf legal entity / billing entity) or off `Location__c` (physical warehouse)? Almost certainly **Entity**, since Net 15 vs Net 30 is an AR term, not a fulfillment attribute. Update AC3 and AC6 accordingly.

    - `QA_CreditController` — does not exist anywhere in either repo.
    - `P_MerchantController` — does not exist anywhere in either repo.
    - There is no "OHFY-Core" package; the repo is split into OHFY-Data-Model, OHFY-Utilities, OHFY-Service-Locator, OHFY-PLTFM, OHFY-OMS, OHFY-WMS, OHFY-REX, plus the four UI packages, plus the dependent OHFY-Ecom.

- **Real integration surface for the portal side:**

#### 5. `Credit__c` namespace collision **(HIGH IMPACT)**

- **Ticket says (AC1):** introduces `Credit_Limit__c`, `Credit_Status__c`, `Credit_Last_Reviewed__c`, `Available_Credit__c` on `Account`.
- **Code shows:** `Credit__c` is already a first-class custom object — 33 fields, in `OHFY-Data-Model/.../objects/Credit__c/`. It models **OMS credit memos / refund credits / credit notes** (linked to invoices and deliveries). And `Account.Total_Credits_Available__c` is a roll-up of those credit memos — completely different semantically from the AC's `Available_Credit__c = Credit_Limit − Outstanding_Balance`.
- **Assessment:** Two different "credit" concepts will coexist on Account with confusingly similar names. Future devs (and AR users) will conflate them.
- **Fix:** rename the new fields to disambiguate. Suggested: `Credit_Line_Limit__c`, `Credit_Line_Status__c`, `Credit_Line_Last_Reviewed__c`, `Credit_Line_Available__c` (or `Credit_Headroom__c`). Or keep the AC names but explicitly label them in the LWC as **"Credit line"** to distinguish from credit memos.

### Incomplete

#### 6. AC1 says "all new, none exist today" but adjacent fields already exist on Account

- **Code shows:** `Account` already carries `Payment_Terms__c` (picklist), `Account_Balance__c`, `Credits_On_Invoice__c`, `Total_Credits_Available__c` (rollup), `Total_Credits_Applied__c`, `Total_Remaining_Credits__c`, `Payment_Method__c`, `Payment_Partner__c`, `Keg_Deposit_Credit_Amount__c`.
- **Assessment:** The six fields AC1 introduces are genuinely missing — so the literal claim is correct — but the ticket should acknowledge the adjacent existing fields and state explicitly:
    - Is **`Account_Balance__c`** reused as the new `Outstanding_Balance__c`, or are these distinct?
    - Is **`Payment_Terms__c`** the source for AC2's "Credit Terms = 'Net 30'" display? (Almost certainly yes — but the ticket never says so.)
    - Is **`Total_Credits_Available__c`** left alone, or does the AC1 `Available_Credit__c` shadow / replace it?
- **Fix:** add an "Adjacent existing fields" note to the description explicitly listing these and saying which the story reuses vs. ignores.

#### 7. Multi-entity model (AC6) is ambiguous **(HIGH IMPACT — design fork)**

- **Ticket says (AC6):** "Given a retailer has **separate accounts** with Gulf's Milton FL entity (Net 15) and Mobile AL entity (Net 30) … credit terms displayed separately per warehouse entity."
- **Code shows:** No existing pattern for "credit per entity per account." `Entity__c` lookups exist on `Receipt__c.Entity__c` and as a standalone object directory, but no Account-to-Entity-credit relationship.
- **Assessment:** AC6 wording ("separate accounts") implies the multi-entity case is modeled as **multiple `Account` records** (one per Gulf entity the retailer trades with) linked through a parent or a household. That is one valid design. The alternative is **one `Account` with credit broken out per Entity via a junction** (e.g., `Account_Credit_Profile__c` with lookups to `Account` and `Entity__c`). The two designs have very different implications for AC1:
    - If multiple Accounts → the 6 new fields go on `Account` as-is (one row per retailer-per-entity).
    - If one Account + junction → the 6 new fields go on the **junction** object, not on `Account`; the LWC iterates the junction rows.
- **Fix:** decide before refinement. Strong recommendation: **junction** — Gulf's reality (one retailer trading with multiple Gulf legal entities) is exactly what a junction is for, and modelling each retailer-entity tuple as its own `Account` will break a dozen other features that assume `Account` = retailer.
