Scaling /code-review to Large PRs — and What "Iterating" Actually Means

Your team is shipping fast, and PRs are getting too big to review by hand — so you lean on /code-review for a good first sweep. But a 12,000-line PR is a lot to ask of a tool built for normal-sized ones. This lesson explains exactly where it breaks, what the change you just made (PR #578) fixes, and — since you said you weren't sure what you were iterating on — names the handful of knobs you're actually turning.

The one thing to hold onto You are not iterating on "quality" in the abstract. You are iterating on one concrete question: can the first sweep reliably surface the load-bearing issues on a large PR without drowning? Everything below is in service of that sentence.

1. Why a big PR breaks the normal review

In Lesson 1 the enemy was human fatigue — reviewers lose accuracy past ~200–400 lines. The automated finder doesn't get tired, but it has its own version of the same limit, plus a second problem baked into the skill:

  • Context saturation. One finder agent reading all 12k lines across 100 files can't hold it all with precision — the tail of the diff gets a shallower read than the top. Same failure shape as human fatigue, different cause.
  • The flat finding cap. The skill stops at ~15 findings even at max effort — a sane limit on a 300-line PR, an artificial lid on a 12k-line one. That's roughly one note per 800 lines, whether or not there are more real issues.
  • No sense of structure. A monorepo PR isn't one flat blob — it's changes across packages that depend on each other. A single pass sees a new shared API and its consumers as unrelated code thousands of lines apart, with nothing connecting them.
The real example this is built on PR #560 (eCommerce Phase 2): 12,228 lines, 100 files. It adds a global pricing method in OHFY-OMS and uses it across a dozen OHFY-eCommerce-UI components. A released global signature is frozen the moment it merges — you can never change it again. That is exactly the kind of high-consequence, hard-to-reverse thing a first sweep must not miss, and exactly what a flat 15-finding pass is most likely to let slip.

2. What PR #578 changes

Below a size threshold (~1,200 changed lines / 20 files), nothing changes — small PRs run exactly as they do today. That was a deliberate constraint: the fix for big PRs must not cost you anything on the common small ones. Above the threshold, the skill switches on two new behaviours:

a. Chunk by package

Split the diff into one chunk per Salesforce package touched (OMS, eCommerce, eCommerce-UI, …), and give each chunk its own reviewer that sees only ~1–4k lines it can actually hold. The finding cap scales with the number of chunks instead of staying flat. This is the fix for context saturation and the artificial lid.

b. Review in dependency order (the "parent/grandparent" part)

The chunks aren't blind to each other. The skill reads the repo's own sfdx-project.json to learn which package depends on which, then reviews them in waves — parents before children. When a parent's contract changes, a short digest of that change is handed forward, so the child's reviewer checks its usage against the new contract instead of discovering it cold. For PR #560 the waves come out as:

Wave 1OHFY-Data-Modelno touched dependency
Wave 2OHFY-OMSdigest: +global eligiblePromotionsByItem()
Wave 3OHFY-eCommercedigest: +global CheckoutSummaryDTO
Wave 4OHFY-eCommerce-UIverifies usage vs. new contracts

Two things make this safe rather than clever: it's derived, so it needs no hand-maintained package list and survives repo reorganization; and sequencing only kicks in when touched packages actually depend on each other — a PR touching just WMS and WMS-UI with no shared change still runs everything in parallel, like before.

Honest limit — say this out loud to the team Chunking trades "one reviewer sees everything, shallowly" for "each reviewer sees its slice deeply." That's the right trade at 12k lines, but it is not strictly more coverage: a bug whose two halves live in different packages and isn't a declared-dependency contract change can now fall between chunks. More total agents also means more tokens and, for a deep dependency chain, more wall-clock. These are deliberate trades, not free wins.

3. Ship it — as the thing it is

Recommendation

Ship PR #578 as a first-sweep improvement, not a quality guarantee.

A "first sweep" has a specific, achievable job: drown-proof the reviewer on large diffs, and make sure the high-consequence, hard-to-reverse things surface (frozen contracts, blockers, cross-tier breakage) so a human isn't hunting across 100 files for them. #578 is squarely aimed at that. It is strictly better than the flat single pass on large PRs and changes nothing on small ones — so there's no reason to hold it.

What it is not is a promise that the review is complete or correct. That distinction is the whole reason the word "sweep" matters: it reduces the human's surface area, it doesn't remove the human. Frame it that way when you tell the team, and it will be trusted for exactly what it does.

4. So what are you iterating on?

Here's the part you said felt fuzzy. "Improving code review" is too vague to act on. In practice you are turning four specific knobs, and iterating means running the tool on a real PR, watching one of these misbehave, and adjusting it:

KnobWhat it controlsYou'd change it when…
ThresholdHow big a PR must be before chunking turns on (~1,200 lines / 20 files)Small PRs start getting chunked needlessly, or medium PRs still feel under-reviewed.
Chunk boundaryHow the diff is split (currently: one chunk per package)A single package's chunk is itself too big, or unrelated files keep landing together.
Finding capHow many findings survive per chunk / overallOutput is a wall of noise, or clearly truncating real issues.
DigestWhat contract info crosses from a parent chunk to a childCross-tier issues still slip through, or the digest carries noise the child doesn't need.

And the loop those knobs live inside has three rungs, cheapest first. You do not need the expensive one to start:

1 · ObserveRun it on one real large PR (#560 is right there). Read the output like a human: does it catch the load-bearing stuff? Is the noise tolerable?
→
2 · TuneAdjust one knob above based on what you saw. Re-run. That is a full iteration.
→
3 · MeasureLater, and optional: run before-vs-after on merged PRs with known bugs, count catches. This turns "I think it helps" into a number.

Rung 3 is how you'd eventually prove quality or catch a regression from a future prompt edit — worth it down the line, but not a prerequisite for shipping a better sweep now. Most of your iterating will be rung 1 → rung 2.

Your memory hook

What the change does — SPLIT then STACK
SPLIT by package · STACK in dependency order

Split so no reviewer drowns in 12k lines; stack so a child package hears what its parent changed before it reviews. Below the threshold, neither happens — small PRs are untouched.

What you're iterating on — T.C.F.D.
Threshold · Chunk boundary · Finding cap · Digest

Four knobs. Iterating = run on a real PR, watch one misbehave, turn it, re-run. Measure only when you need a number.

If someone asks "what did you actually improve, and is the review now guaranteed good?" Say: "On large multi-package PRs it now splits by package and stacks the review in dependency order, so it doesn't drown and it catches cross-tier contract changes — that's a better first sweep, not a guarantee. Small PRs are untouched." That one sentence is the whole lesson.
