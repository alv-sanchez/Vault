Lesson 0001 · Safety Stock Epic (BMS-5068)

How Safety Stock Actually Flows Through the System

You own this epic and can run it — but the piece that stays fuzzy is the chain: how does a planner deciding “hold more of this SKU” turn into a bigger purchase order? This lesson walks that one chain, end to end, using the real classes in the repo. One tangible win: by the end you can narrate the flow out loud without notes.

1. First, what “safety stock” even is here

The trap is imagining a stored “safety stock quantity” sitting on a record. There isn't one. In this system, safety stock is an upward adjustment to the target Days-on-Hand (DOH) — the number of days of forward demand you want the inventory to cover.

Standard target might be 10 days. A planner worried about a supplier says “make it 16 for this SKU.” That 16 isn't a new concept bolted on — it's the same target DOH the replenishment engine already reads, just resolved to a higher value. That single reframing is why the whole epic could reuse existing plumbing (Lesson 2).

Say it in one sentence Safety stock = a higher target DOH, resolved per (item, location, supplier) at calculation time — never a separately stored buffer quantity.

2. The chain, one rung at a time

Every rung is a real thing in the repo. The badge is the component that owns that step.

SET
A planner creates an override. A row in SKU_Override__c — scoped to a SKU (item+location) or to a whole supplier (Account) — carrying Target_DOH_Override__c, effective dates, a reason, and a status. SKU_Override__c · scope + lifecycle added by BMS-5636
RESOLVE
The resolver picks the effective target. S_InventoryThresholds.resolve(itemId, locationId, accountId) walks a waterfall and returns a Result with targetDOH and a resolutionSource label. Precedence: active SKU override → active supplier override → static baseline tiers → system default. First non-null field wins, per field. S_InventoryThresholds.cls — the precedence is in the class header comment
SIZE
The target becomes a case quantity. S_ReplenishmentOrderSizing.size(...) computes targetCases = round(targetDOH × Average_Daily_Depletion__c ÷ Units_Per_Case__c), then rounds to the nearest layer/pallet boundary. A higher target DOH ⇒ more cases ordered. This is where the planner's decision becomes purchasing behavior. S_ReplenishmentOrderSizing.cls (BMS-4217) — the DOH engine
FREEZE
The number and its origin get stamped on the task. Effective_Target_DOH__c and Resolution_Source__c are written onto Replenishment_Task__c at generation time, so the audit record says “we ordered to 16 days because of a SKU Override” — and stays true even after the override expires. Replenishment_Task__c fields (BMS-5639)
CLOSE
The override ends and the target reverts. A nightly batch flips Scheduled→Active→Expired on the dates; a planner can also close early with a reason. On expiry/approach the creator is notified. Next calculation resolves back to the standard target — no code change, no manual cleanup. BA_SKUOverride_ExpirationProcessor + S_SafetyStockNotifier (BMS-5638)

3. The safety valve you should remember

The sizing engine has an explicit fallback contract: if targetDOH or velocity is null or non-positive — an unconfigured SKU, or one with no depletion data — size() returns the pre-existing capacity-fill quantity unchanged. So the DOH path is purely additive: SKUs nobody has touched size exactly as they did before this epic. That's why shipping it couldn't regress existing replenishment.

Grounded in the code The SizingResult even carries a dohDriven boolean — true when the target drove the number, false when it fell back. The system tells you which path it took.
