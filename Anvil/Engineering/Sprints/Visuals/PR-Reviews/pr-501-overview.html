🧭 The five-phase pipeline

1

Acquire

Paginated PR file listing (plain gh pr view --json files truncates at 100 files — a real problem, since the validation PR itself had 956 changed files). Partitions feature code from retrieve-noise, walks the schema dependency closure, and classifies schema that exists in neither repo as org-only. Checks for in-flight/completed overlap — if a prior port already exists on main, pivots to a delta port (gap-fill only, never regresses product-ahead code).

2

Productization Map Hard approval gate

The one checkpoint that blocks all code. Reuse-first data-model mapping with a field-level rename table (e.g. demo ohfy__Active__c ≠ product Is_Active__c — same-looking field, different reality), component-mapping with namespace-wide class-name collision checks, and platform risk flags (Visualforce, external libraries, CSP, secrets sitting in Custom Metadata). Nothing is written until this map is explicitly approved.

3

Port

Follows references/translation-guide.md: routes all reads/writes through QueryService/DmlService, wires into the trigger framework, generates _T/Jest tests, hoists DTOs per ADR-0007, builds the UI-wrapper facade, mirrors both org-metadata folders, and sets up Named Credentials for any callouts — the demo's shortcuts become the product's conventions.

4

Deploy & verify

Claims a pool org (never a raw scratch org), deploys in tier order, cascade-selects which Apex tests to run, walks the feature's behavior live via Chrome DevTools, and — when a demo org is connected — runs a read-only side-by-side parity check against it. Playwright is now required, not conditional, for any Tier-4 (UI) touch.

5

Pre-PR gate & PR

Runs the full CLAUDE.md check suite, commits in tier order with conventional-commit + ticket-key messages, and opens a single draft PR.

⚠️ Notes & decisions

The Productization Map gate is the load-bearing safety mechanism here. Everything before it (acquire) is read-only analysis; everything after it (port/deploy/PR) is automated. The field-level rename table specifically exists because a demo field and a product field can share a name while meaning different things — skipping this gate is exactly how a demo's shortcuts leak into the managed package.
This PR quietly raises the bar for every future Tier-4 PR, not just ones built by this skill — the CLAUDE.md change makes Playwright non-optional org-wide. Worth knowing if you're mid-flight on a UI PR without Playwright coverage.
One feature per invocation by design. If a Sales-Demos PR bundles several features, the skill asks which one to port rather than trying to do all of them — a large demo PR is already a long run on its own.
