Front-Line Pricing — Data Model & Resolution

How account-specific pricing flows from Item__c through the FLP cascade to the e-commerce storefront. Single sanctioned resolver: S_FrontLinePricing.resolve() (OHFY-OMS).

ADR-0009 · BMS-3929 · org snapshot: jun9Ecom-Split · seeded by orgScripts/e-commerce/seed-flp-demo.apex · 2026-06-10
What this is: a visual guide to the front-line-pricing data model and the exact records that exist after running orgScripts/e-commerce/seed-flp-demo.apex. The seed builds every cascade scenario (ITEM, ITEM_TYPE_PKG, ITEM_LINE_PKG, and ITEM_DEFAULT-by-absence/structure) over the seeded beverage catalog. All records are idempotent and tagged External_Id__c = 'flpdemo:…', so revert-flp-demo.apex sweeps them cleanly. The sections below show the object model, the resolution waterfall, and the resulting prices the seed produces.

1 Object model — everything radiates from Item__c

Three sides meet on a price row: the catalog side describes what is being priced (the item and its classification attributes), the account side describes who sees the price (group membership + warehouse), and Front_Line_Price__c is the row in the middle that joins them.

Catalog — what is priced

ohfy__Item__c PRODUCT

  • Item_Type__c → brand (Wave Splitter…)
  • Item_Line__c → portfolio (Beverage)
  • Packaging_Style__c → pkg format
  • Default_Case_Price__c — tier-4 fallback
  • Units_Per_Case__c
The three highlighted lookups are the cascade match keys. No Packaging_Style__c ⇒ tiers 2/3 structurally unreachable (Sticker Pack).

The price row — joins both sides

ohfy__Front_Line_Price__c PRICE

  • Item_Scope_Level__c ITEM | ITEM_TYPE_PKG | ITEM_LINE_PKG
  • Specificity_Score__c formula: 3 / 2 / 1 (never set by hand)
  • Item__c — filled when level = ITEM
  • Item_Type__c + Packaging_Style__c — level = ITEM_TYPE_PKG
  • Item_Line__c + Packaging_Style__c — level = ITEM_LINE_PKG
  • Front_Line_Pricing_Group__c — who
  • Fulfillment_Location__c — which warehouse
  • Case_Price__c · Unit_Price__c — the money (unit ≠ derived)
  • Start_Date__c · End_Date__c — the real gate
  • Status__c Draft/Cancelled excluded; rest date-gated
Status is system-maintained: insert as Upcoming; the nightly schedulable promotes to Active on Start_Date. The resolver admits Upcoming / Superseded / Expired rows and lets the dates decide — only Draft and Cancelled are out.

S_FrontLinePricing.resolve() RESOLVER

  • in: itemId + accountId + fulfillmentLocationId + asOfDate
  • out: resolutionPath + casePrice + unitPrice + flpId
Max 3 SOQL queries per bulk call regardless of request count. Every consumer (storefront, invoicing, credits, integrations) goes through here — nobody computes their own waterfall.

2 The resolution waterfall — most specific wins

Among rows that pass the eligibility gates, the highest Specificity_Score__c wins. Ties break on newest Start_Date, then highest Id. Tiers 4 and “NONE” live in resolver code, not in the score.

3
ITEM
FLP row’s Item__c == the item — one exact product
Wave Splitter: 1/6 BBL → $69
2
ITEM_TYPE_PKG
row’s Item_Type__c + Packaging_Style__c == item’s brand + format
Sharks Fin + Can Case → $17
1
ITEM_LINE_PKG
row’s Item_Line__c + Packaging_Style__c == item’s portfolio + format
Beverage + 1/2 BBL Keg → $160 (all brands)
—
ITEM_DEFAULT
no FLP row matched → fall back to Item__c.Default_Case_Price__c (unit price = null)
all 1/4 BBLs, Sticker Pack
∅
NONE
no match and no default → null prices; storefront renders “Call for pricing”
never silently $0
Eligibility gates (checked before any score comparison): same Fulfillment_Location__c as the account  ·  FLP row belongs to the account’s active pricing group (junction date window covers asOfDate)  ·  Start/End dates cover asOfDate  ·  Status ∉ {Draft, Cancelled}  ·  scope lookups actually match the item’s attributes. A score-3 row failing any gate is simply invisible.

4 How the storefront consumes it

userDataService (LWC)

On login: fetch catalog, seed itemToUnitPriceMap from Default_Case_Price__c. 5-min cache.

resolveCatalogPricing (Apex)

Calls S_FrontLinePricing.resolve() for every catalog item with the account + warehouse, asOfDate = today.

itemToUnitPriceMap

Resolved case prices overwrite the defaults. NONE flags the item _callForPricing.

ecomShop / reorderModal

Shop tiles show the resolved price. Reorder compares it against the invoice line’s stored historical price.

Reorder strikethrough (BMS-3929): original = invoice line’s stored Case_Price__c || Unit_Price__c (immutable history) · current = resolver output. Differ by ≥ $0.01 ⇒ $65.00 $69.00 + amber “updated pricing” banner. Item dropped from the pricelist ⇒ red “No longer on pricelist” and the line can’t be reordered. To simulate a price change, change the catalog side (FLP row / default) — never the invoice line.
The two-price trap on Invoice_Item__c: every invoice line stores BOTH Case_Price__c (per case — what subtotals are computed from) and Unit_Price__c (per individual unit: Case_Price ÷ Units_Per_Case, e.g. $15 case ⇒ $0.625/can). All catalog-side prices (itemToUnitPriceMap, FLP Case_Price__c, Default_Case_Price) are per case — always compare case-to-case. A “$0.63 vs $17.00” comparison means someone grabbed the per-can field; for kegs (Units_Per_Case = 1) the two fields coincide, which hides the mistake. Fixed 2026-06-10 in ecomOrderHistory.js (case price preferred) and reorderModal.js (footer total repriced on open).

5 Tracking queries

Copy-paste ready for sf data query -o jun9Ecom-Split -q "…". The last one runs the real resolver.

All FLP rows — full scope, most specific first
SELECT Name, ohfy__Item_Scope_Level__c, ohfy__Specificity_Score__c,
       ohfy__Item__r.Name, ohfy__Item_Type__r.Name, ohfy__Item_Line__r.Name,
       ohfy__Packaging_Style__r.Name, ohfy__Case_Price__c, ohfy__Unit_Price__c,
       ohfy__Status__c, ohfy__Start_Date__c, ohfy__End_Date__c,
       ohfy__Fulfillment_Location__r.Name, ohfy__Front_Line_Pricing_Group__r.Name
FROM ohfy__Front_Line_Price__c
ORDER BY ohfy__Specificity_Score__c DESC
Account memberships — who is in which pricing code
SELECT ohfy__Account__r.Name, ohfy__Front_Line_Pricing_Group__r.Name,
       ohfy__Effective_Date__c, ohfy__End_Date__c, ohfy__Is_Active__c
FROM ohfy__Account_Pricing_Group__c
ORDER BY ohfy__Account__r.Name
Item match-readiness — which tiers each item can hit
SELECT Name, ohfy__Item_Type__r.Name, ohfy__Item_Line__r.Name,
       ohfy__Packaging_Style__r.Name, ohfy__Default_Case_Price__c
FROM ohfy__Item__c
ORDER BY ohfy__Packaging_Style__r.Name NULLS LAST, Name
Items that can never match tiers 2/3 (no packaging style)
SELECT Name FROM ohfy__Item__c WHERE ohfy__Packaging_Style__c = null
