Cycle Counts — how they're pulled & what "Verify" does

Object: Inventory_Log_Group__c (a cycle-count batch) · service: S_CycleCountVerification

Two different reads

📄 On checklist load

Shows only counts already tied to THIS checklist.
getForChecklist → WHERE Shift_End_Checklist__c = thisChecklist
A fresh checklist shows zero until you Verify.

✅ On "Verify cycle counts"

Finds untied counts for this warehouse+date and ties them.
verify() → candidate filter → link → refresh count

What Verify does, step by step

  1. Load checklist — read its Warehouse + Shift Date; resolve warehouse Id → Name ("Milton FL").
  2. Find candidates — Inventory_Log_Group__c where:
    Is_Cycle_Count__c = TRUE · Log_Date__c = shift date · Location__r.Warehouse__c = "Milton FL" · Shift_End_Checklist__c = NULL
  3. Tie them (the write) — set Shift_End_Checklist__c = this checklist on each  DmlService.doUpdate
  4. Refresh count — set Shift_End_Checklist__c.Cycle_Count_Groups__c = tied total (feeds the finance rollup at submit).
  5. Return the now-tied list → table re-renders + toast "1 cycle count tied to this shift."
Verify = link, not approve. It never touches Is_Approved__c — so the row stays Pending. Approval is the separate Inventory-Count workflow's job.

Why only the Day shift shows ILG-000000

  • A cycle count has no shift field — it's keyed by warehouse + date only (Location + Log_Date).
  • When Day verified, it stamped ILG-000000.Shift_End_Checklist__c = Day checklist.
  • Now Mid / Night show nothing: their load reads WHERE Shift_End_Checklist__c = (that shift's checklist) — ILG is tied to Day, not them — and Verify only picks up = NULL (untied) rows, so it's excluded.
  • Net: first shift to verify claims the day's counts (idempotent; never re-links a count already tied elsewhere).
Known design gap (flagged to PO as BMS-4079 multi-shift attribution): because counts aren't shift-stamped, on a multi-shift day attribution is first-come. Splitting counts per shift is an open product decision, not built.
