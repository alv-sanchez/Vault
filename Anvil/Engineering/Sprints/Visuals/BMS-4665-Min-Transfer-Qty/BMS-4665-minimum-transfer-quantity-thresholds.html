Minimum Transfer Quantity Thresholds

Stop small, uneconomical inter-warehouse transfers from committing. Enforce per-item minimums (in cases, layers, or pallets) and layer/pallet rounding at the New → In Progress status transition. Built Salesforce-native (Spec B) on PR #355 — what was greenfield is now implemented and tested.

01 Why this exists

The problem

Gulf wants inter-warehouse transfers to respect minimum quantity thresholds and layer/pallet rounding rules, so trivial transfers (e.g. 3 loose cases) don't get committed and clog the lane.

Today there's nothing stopping them — no minimum or rounding enforcement exists anywhere on transfers in OHFY-Split.

Where it plugs in

The real enforcement gate is the Transfer_Group__c status machine. There is no Draft status — "enforce before commit" maps to the New → In Progress transition.

04 Two implementation paths — Spec B was chosen & shipped

SPEC A · NOT TAKEN

Off-Platform

transfer-thresholds config in Mongo, validated in the off-platform planning flow (pairs with BMS-4661 Spec A)

Pro

  • Threshold config/UX iterates without managed-package releases
  • Complex lane-level rules & simulations are cheap off-platform
  • No 2GP schema freeze for the config shape

Con

  • Cannot enforce alone — SF users can advance groups directly, bypassing the rule; an on-platform guard is still required (dual deploy)
  • SF write-back auth / idempotency net-new; no CDK deploy stack
  • Config split across two systems for one business rule
  • Item/location reference via SalesforceService.queryAll sync
  • JWT-bearer flow for the unattended worker
SPEC B · ✓ SHIPPED

Salesforce-Native

New Transfer_Threshold__c object + enforcement in TransferGroupTriggerService

Pro

  • Single enforcement point inside the status machine — no bypass path
  • Inventory_Threshold__c precedent de-risks the config model
  • Native admin UI / permissions for threshold maintenance

Con

  • New config object/fields = frozen 2GP surface once released
  • Managed-package cadence for non-data-driven rule changes
  • Trigger-time resolution adds SOQL to a hot path — must stay bulk-safe
  • Item__c + origin/dest Location__c lookups (null = global), Min_Quantity__c + Quantity_Unit__c, Enforce_Layer_Pallet_Rounding__c, Notes__c, Is_Active__c, External_Id__c
  • Layers/Pallets convert to cases via Item Cases_Per_Layer__c / Cases_Per_Pallet__c
Spec B was implemented. Spec A can't enforce on its own — SF-side users bypass the off-platform flow, so an on-platform guard is required regardless, collapsing Spec A into "Spec B plus a second system." Spec B gives a single enforcement point inside the status machine; threshold resolution is bulk-safe (two queries, no SOQL in loops). The Inventory_Threshold__c precedent de-risked the config model.

06 Verified constraints — don't trip these

✗ No Draft status

Don't invent a draft-finalization event. Enforcement maps to the New → In Progress transition (or creation-time validation).

✗ Keep out of TransferTriggerService

Enforcement is a status-gate concern, not inventory math. Touching adjustment logic risks bucket math & Should_Bypass_Adjustment__c regressions.

✗ Hot-path SOQL

Trigger-time threshold resolution must stay bulk-safe — resolve applicable thresholds via QueryService without per-record queries.
