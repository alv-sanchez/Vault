Ticket Context

Acceptance Criteria

Reorder resolves current pricelist pricing

Reorder modal lines display the current price from the account's active pricelist, not the historical invoice price. Changed lines show the original price struck through alongside the current price, a summary note counts updated items, and items no longer on the pricelist are flagged unavailable for reorder.

Cancelled orders visible in order history

Cancelled orders appear alongside all other statuses with a clear status badge and the Cancelled_Reason__c value, show no Reorder action, and "Cancelled" is a filterable status option.

Fulfillment location displayed in order history

Each order shows the Fulfillment Location name (desktop table and mobile cards), sourced from the existing Fulfillment_Location__c lookup on Invoice__c.

Pricing Resolution Hierarchy

How S_FrontLinePricing.resolve() picks a price for each catalog item (per ADR-0009). The ecom flow calls it via userDataService.resolveAccountPricing() → Ecom_UI_Wrappers.resolveCatalogPricing(accountId, fulfillmentLocationId, itemIds) with asOfDate = today. Every Front_Line_Price__c candidate must match the account's warehouse AND the account's active pricing group AND cover the as-of date — the cascade only ranks rows that pass all three gates.

What Was Built

This branch closes the three gap-fill acceptance criteria from the polished BMS-3929 scope. The reorder modal now resolves current pricelist pricing instead of replaying historical invoice prices — showing struck-through original prices, an "N items have updated pricing" banner, and flagging items that dropped off the account's pricelist as unorderable. Cancelled orders are now visible in order history with a status badge and the Cancelled_Reason__c value, with the Reorder action suppressed. The Fulfillment Location name renders in both desktop and mobile order layouts. The work also wires in the front-line pricing cascade: a new resolveCatalogPricing wrapper resolves account/warehouse-specific pricing at catalog load via S_FrontLinePricing, and items the resolver can't price (resolutionPath = NONE) render a "Call for Pricing" state in the shop instead of silently pricing at zero.

Key Decisions

  1. Pricing comparison is done client-side in the reorder modal against the pricelist data userDataService has already loaded for the shop — no extra Apex round-trip per modal open.
  2. Front-line pricing is resolved once per session at catalog load (resolveAccountPricing() inside init), overriding the shared unit-price maps — so the shop, cart, and reorder modal all consume resolved prices from the same cache for free.
  3. NONE resolution renders "Call for Pricing" and removes the Add-to-Cart control rather than falling back to a zero or stale price — per the ADR-0009 §17.8 contract: never silently invoice at zero.
  4. Items missing from the active pricelist are kept visible but unorderable in the reorder modal (treated like out-of-stock with a distinct "No longer on pricelist" label) instead of being hidden — preserving the audit/visibility intent of the ticket.
  5. A 1-cent epsilon (Math.abs(diff) >= 0.01) gates the price-changed flag, avoiding float-noise banners.
  6. Cancelled visibility was implemented by relaxing the single SOQL filter (exclude only Draft) rather than adding a separate query path or toggle — the existing Cancelled status filter option in the UI becomes functional with no new UI state.
  7. The pricing resolver failure path falls back silently to Default_Case_Price__c with a console.warn — a pricing-infra outage degrades to catalog defaults instead of breaking the shop.
