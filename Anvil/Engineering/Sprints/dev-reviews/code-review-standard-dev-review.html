1+# Code Review Instructions
2+
3+Instructions and guardrails for Claude when reviewing pull requests in this repo — whether via `/code-review`, or an ad-hoc review request. Read this file in full before producing any review output.
4+
5+## Review Flow
6+
7+1. **Understand intent first.** Read the PR description and the linked BMS ticket — especially its acceptance criteria — before reading any code. The diff is judged against what it claims to do, not what the reviewer imagines it should do.
8+2. **Scan the shape of the diff.** Which packages/tiers are touched, which file types (Apex, LWC, metadata), how big it is. This determines which Repo-Specific Checks apply and how deep the Audit Criteria pass needs to go.
9+3. **Review the diff** — Repo-Specific Checks first (hard rules, all blockers), then Audit Criteria (judgment areas). Collect findings, questions, high-impact decisions, and kudos as you encounter them rather than reconstructing them at the end.
10+4. **Write up** using the Output Format below.
11+
12+## Scope & Guardrails
13+
14+- The diff is the subject of the review, not the boundary of attention. Read whatever surrounding code, callers, tests, or git history is needed to judge the diff correctly.
15+- Pre-existing or adjacent issues outside the diff are fair game when the diff touches, worsens, or builds on them — report them under **🔭 Beyond the Diff** so the author can tell them apart from blockers on their own changes. Don't turn this into a general audit of untouched files.
16+- Noise control comes from the severity bar, not a finding count: report everything that genuinely earns its severity label, and skip nits that wouldn't change the merge decision.
17+- Do not make code changes, commits, or pushes during a review — output findings only.
18+- If a check can't be evaluated from the diff alone (e.g., whether tests pass), say so explicitly instead of guessing.
19+- Frontend visual quality in the internal Tier-4 UI packages (`OHFY-PLTFM-UI/`, `OHFY-OMS-UI/`, `OHFY-WMS-UI/`, `OHFY-REX-UI/`) is judged against `.claude/skills/ohfy-design/SKILL.md`, not generic taste. `OHFY-eCommerce-UI/` is excluded — it's an Experience Cloud (LWR) site outside the internal LWC design system.
20+
21+## Ask, Don't Assume
22+
23+The goal is a review the author can act on with full confidence — which means the reviewer must not paper over gaps in its own understanding.
24+
25+**Never assume business or architecture intent that isn't visible in the diff, the linked ticket, or repo docs.** Concretely, do NOT:
26+
27+- Assume a branch, flag, or threshold is wrong because it differs from a generic industry pattern — this repo's conventions (CLAUDE.md, `docs/engineering/adrs/`, `docs/security/mode-selection.md`, per-package CLAUDE.md) are the standard, and domain rules (beverage distribution: territories, allocations, compliance holds) often look unusual by design.
28+- Assume what production data looks like (e.g., "this lookup is always populated", "quantities can't be negative") — data-shape claims need a schema default, validation rule, or trigger in evidence.
29+- Assume why an existing pattern was chosen, or that deviating from it in this PR is accidental — it may be a deliberate migration step.
30+
31+**When a finding depends on missing context, downgrade it to a question instead of guessing in either direction.** But do the homework first: check the linked ticket, `docs/engineering/adrs/`, git history, and the existing tests — ask only what those can't settle. Put surviving questions in a dedicated **❓ Questions for the Author** section, each phrased so the author can answer in one or two sentences, e.g.:
32+
33+> ❓ `S_CreditAllocation.cls:142` — the new guard skips allocation when `Territory__c` is null. Is a null territory a real state in production data, or should this throw? If it's real, the silent skip needs a Logger call.
34+
35+A review with two precise questions beats one with two confident-but-wrong blockers.
36+
37+## High-Impact / Cost-of-Change Decisions
38+
39+Every review comment must include a **🧭 High-Impact Decisions** section (omit only if the PR is genuinely trivial) summarizing decisions in this PR that are expensive or impossible to reverse later — even when they're not problems. The author and future readers should be able to see at a glance what this PR commits the codebase to. In a managed-package repo, look especially for:
40+
41+- **Permanent package API surface**: new/changed `global` classes, methods, or DTO properties; `@AuraEnabled` method signatures; `@namespaceAccessible` members. Once released in the `ohfy` managed package these can never be removed or re-typed.
42+- **Schema**: new objects, fields, picklist values, or relationship changes — fields on released managed objects are effectively forever.
43+- **Cross-package dependencies**: a Tier-3 package newly calling into another package, new `Service_Configuration__mdt` / ServiceLocator wiring, or anything that changes the dependency tiers.
44+- **Integration & data contracts**: External ID formats, webhook/callout payload shapes, CMDT-driven configuration shapes that customer orgs will populate.
45+- **Behavioral defaults**: changes to trigger behavior, sharing/access mode, or allOrNone semantics that all downstream features inherit.
46+
47+For each, give one sentence: what was decided and what it locks in.
48+
49+Litmus test: if reversing the decision later would take a managed-package major release, a data migration, or customer coordination, it belongs in this section.
50+
51+## Kudos
52+
53+Include a **👏 Kudos** section calling out genuinely good work in the diff — positive reinforcement is part of the review, not filler. Be specific and cite lines, e.g., a bulk-safe rewrite, an edge case covered in tests that would have been easy to miss, a well-placed Logger call, complexity removed, or a naming/doc improvement. One to three items; skip generic praise ("nice clean code") — if you can't point at a line and say why it's good, leave it out.
54+
55+## Repo-Specific Checks
56+
57+Every item here is a hard rule — a violation is a **[BLOCKER]** no matter how small the diff. The linked docs are authoritative when a case looks ambiguous.
58+
59+- **No raw SOQL/DML** in non-test `.cls` files — all reads go through `QueryService`, all writes through `DmlService`. Flag any added `[SELECT`, raw `insert/update/delete/upsert/undelete`, or `Database.*` call.
60+- **Explicit `AccessLevel.SYSTEM_MODE`** must have an inline comment on the line above citing rule 1, 2, 3, 4, or 6 from `docs/security/mode-selection.md`. A rule-5 citation is a block.
61+- **No explicit `AccessLevel.USER_MODE`** in non-test classes — it defeats the bypass-permission default (ADR-0011). Use `AccessLevelResolver.getDefaultAccessLevel()` or omit the argument entirely.
62+- **Logger in every catch block**: `Logger.getInstance().error('<Class>.<method> ...', e)` followed by `flush()`, including "ignored" catches. Test classes exempt.
63+- **DTO pattern (ADR-0007)**: any custom Apex type crossing an `@AuraEnabled` boundary between packages must be a `global` DTO with `{ get; set; }` properties and a single parameterless constructor.
64+- **Apex test coverage**: every added/modified Apex method must be exercised with assertions by a `_T` class.
65+- **org-metadata mirroring**: FlexiPage/layout/tab/quickAction changes must appear in both `org-metadata/managed/` (with `ohfy` prefix) and `org-metadata/scratch/` (unprefixed).
66+- **Field/object standards**: any new or changed field, object, or relationship follows `docs/engineering/standards/naming-conventions.md` and `quantity-conventions.md` (base-unit source of truth, `Quantity_{State}__c` / `Units_{Verb}__c` patterns).
67+- **Conventional commits** with a `BMS-XXXX` ticket key on every commit.
68+
69+## Audit Criteria
70+
71+Judgment areas that apply to any diff, on top of the hard rules above. Findings here carry whatever severity the evidence supports.
72+
73+### Bugs & Runtime Errors
74+
75+Flag any code that will or is likely to cause a runtime error:
76+
77+- Divide by zero (literal or unchecked denominator)
78+- Null dereference — accessing a property or method on a value that could be null/undefined without a prior null check
79+- Reading an undefined variable or uninitialized value
80+- Index out of bounds — array/list access without a size check
81+- SOQL queries inside loops (Apex governor limit violation)
82+- DML statements inside loops (Apex governor limit violation)
83+- Synchronous callouts inside async contexts or vice versa in LWC/Aura (e.g., calling an `@wire` adapter result directly as if it's a Promise, mixing `async/await` with raw `.then()` chains in ways that lose error handling)
84+- Race conditions in LWC — e.g., mutating shared reactive properties from multiple concurrent `async` methods without coordination
85+- Maps or Sets that can silently overwrite keys — flag any `Map.put()` or object spread where the key is not guaranteed unique and the overwrite is likely unintentional
86+- Missing `break` in switch statements where fall-through is not intentional
87+
88+### Silent Failures & Swallowed Errors
89+
90+Flag code paths where an error can occur but will be hidden from the user, logs, or monitoring — especially asynchronous contexts where exceptions never surface to the original transaction. Do **not** just flag the presence of a Queueable/Batch/Future; flag any operation inside one that could realistically fail and isn't caught and recorded:
91+
92+- **Async Apex that can throw but has no error handling** — any Queueable (`execute`), Batchable (`start`/`execute`/`finish`), Future (`@future`), or Schedulable that performs DML, a callout, SOQL, or other failable work without a `try/catch`. An unhandled exception here is invisible to the calling user and is only discoverable in async job logs.
93+- **Empty or swallowing catch blocks** — a `catch` that does nothing, only calls `System.debug()`/`console.error()`, or otherwise discards the exception without rethrowing, logging via `Logger` + `flush()`, or surfacing it to the user.
94+- **Over-broad catch that continues** — catching `Exception` (or bare `catch (e)`) and proceeding as if nothing happened, masking real failures.
95+- **Partial-success DML not inspected** — `DmlService.doInsert(records, false)` / `Database.*(records, false)` (allOrNone=false) or any `SaveResult[]`/`UpsertResult[]`/`DeleteResult[]` where the results are never checked for `isSuccess()`/`getErrors()`, so failed rows vanish silently.
96+- **Queueable without a Finalizer** — when a Queueable does failable work (especially callouts), flag the absence of `System.attachFinalizer()` / a `Finalizer` to catch and record unhandled exceptions and, where appropriate, retry.
97+- **LWC/JavaScript promises with no rejection handling** — an imperative Apex call, `fetch`, or other Promise with no `.catch()` (or no `try/catch` around `await`); a rejected promise leaves the UI inconsistent with no user feedback.
98+- **Failure logged but not surfaced** — work that fails and writes only a `System.debug`/`console.error` with no toast, no Logger record, and no rethrow, so the user believes the action succeeded.
99+
100+For each finding, state *what* can fail and *how* it should be handled (caught + logged durably, surfaced to the user, retried, etc.).
101+
102+### Conditional Logic & Dead Branches
103+
104+Flag conditionals that don't actually branch the way they appear to, or that silently skip work:
105+
106+- **Effectively constant conditions** — an `if`/ternary/`while` whose outcome is fixed given how its variables are assigned (e.g., a flag hardcoded `true` just above the check, `if (x != null)` immediately after `x = new Account()`, `if (list.size() >= 0)`). The "other" branch is unreachable.
107+- **Conditions that almost always take one route** — a check driven by a parameter, custom setting/metadata, or feature flag that in practice is (almost) always the same value, so the alternate path rarely or never runs. Call out the assumption — and per **Ask, Don't Assume**, if you can't determine the real-world value, raise it as a question rather than a verdict.
108+- **Silent conditional skips** — a guard clause (`if (cond) return;`, `continue`, early `break`) that bypasses the method's core work under a condition that is common rather than a true edge case, so the operation silently does nothing without logging or signaling. Distinguish legitimate early-exits (empty input) from skips that quietly drop real work.
109+- **Identical branches** — `if`/`else` arms, both ternary results, or multiple `switch`/`case` branches that execute the same logic, making the condition pointless.
110+- **Unreachable branches** — `else`/`case`/`default` paths that can never be hit given prior `return`/`throw` statements or mutually exclusive earlier conditions.
111+- **Redundant nested conditions** — an inner condition already guaranteed (or already excluded) by an outer one, leaving a dead branch.
112+
113+For each finding, state which branch is effectively dead or always-taken, and why, based on the actual parameter/variable values visible in the diff.
114+
115+### Dead Code
116+
117+- Commented-out blocks of code (more than a single explanatory line)
118+- Unreachable code paths (e.g., code after an unconditional `return`/`throw`)
119+- Unused variables, parameters, or imports
120+
121+### Debug & Logging Statements
122+
123+- `System.debug()` calls left in Apex production code
124+- `console.log()`, `console.warn()`, `console.error()` left in LWC/JavaScript production code
125+- Test-runner escape hatches: `.only(`, `.skip(`, `fdescribe(`, `xit(`
126+
127+### Naming Conventions
128+
129+Apply these rules to all changed files (full conventions: `docs/engineering/standards/naming-conventions.md`):
130+
131+**Salesforce Object & Field Metadata** (`.object-meta.xml`, `.field-meta.xml`):
132+
133+- The `<label>` value and the API name (filename prefix or `<fullName>`) should match, with the only difference being that the API name uses underscores where the label has spaces (e.g., label `Invoice Line Item` → API name `Invoice_Line_Item__c`). Flag mismatches.
134+
135+**Apex Classes & Triggers** (`.cls`, `.trigger`):
136+
137+- Class names must be PascalCase and follow the role prefixes in CLAUDE.md (`E_`, `S_`, `B_`/`BA_`, `Q_`, `_T` suffix for tests)
138+- Method names must be camelCase (e.g., `calculateTotal`, not `CalculateTotal` or `calculate_total`)
139+- Constants should be `UPPER_SNAKE_CASE`
140+
141+**LWC & JavaScript** (`.js`):
142+
143+- Component folder names must be camelCase (the framework enforces this, but flag any mismatch between folder name and class/export name)
144+- Method and function names must be camelCase; class names PascalCase
145+
146+**Custom Metadata & Other Metadata**:
147+
148+- Record API names should follow the same label-to-API-name pattern as objects/fields above
149+
150+## Severity & Reporting
151+
152+- Classify each finding inline:
153+ - **[BLOCKER]** — violates a Repo-Specific Check, or will cause a runtime error, data loss, security issue, or governor limit exception in production
154+ - **[WARNING]** — likely problem or bad practice that should be fixed before merge
155+ - **[SUGGESTION]** — minor style or hygiene issue; fix is optional but recommended
156+- If a finding's severity hinges on context you don't have, it isn't a low-confidence [BLOCKER] — it's a ❓ Question (see Ask, Don't Assume).
157+- Cite findings as `file_path:line_number` against the PR diff.
158+- Do not flag formatting Prettier already enforces, or style preferences not documented in this repo.
159+
